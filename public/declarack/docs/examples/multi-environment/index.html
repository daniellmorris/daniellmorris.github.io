Real multi-environment lab¶

Start two independent Docker Swarms inside Docker, each with one manager and one worker, actual running services, Prometheus, Grafana, and Declarack. Declarack also connects to the outer host Docker engine using its standalone feature set.

This uses four privileged Docker-in-Docker engine containers. It requires a local Docker Engine/Docker Desktop that permits privileged Linux containers, Docker Compose, Python 3 (standard library only), and the host's OpenSSH client/keygen. It was exercised on Docker Desktop with Docker 29.5.2 nested engines. The nested nodes share the outer Linux kernel; they are not separate VMs or physical hosts. Allow a few GB of free disk and memory for images and persistent engine volumes.

The outer host's existing Swarm membership is left unchanged. No host Swarm init, join, or leave command is executed. Selecting standalone features for the host is a Declarack view choice, not a change to the daemon's actual operating mode.

Start¶

From the repository root:

python3 examples/multi-environment/lab.py up --http-mode ssh

The script builds the engine/app/Declarack images, creates local credentials, starts the containers, initializes two distinct Swarms, joins exactly one worker to each, loads job/app images into all four engines, deploys services, provisions monitoring, creates runtime Declarack configs, and verifies real responses. First startup downloads Grafana/Prometheus images and can take several minutes.

The fixed Compose project is declarack-lab. Re-running up reuses its data and keys, verifies membership, reloads local images, and updates its sample services. Image changes may recreate engine containers and roll the sample services; their volumes preserve cluster identity while workloads reconverge. It refuses to reset a manager that is unexpectedly joined as a worker elsewhere. Do not point these commands at an unrelated remote Docker context.

What runs¶

Environment Engine/node layout Workloads
Swarm A swarm-a-manager + swarm-a-worker lab-web: 2 worker replicas; lab-heartbeat: 1 manager replica
Swarm B swarm-b-manager + swarm-b-worker Same services, independently scheduled
Host Docker Your outer Docker daemon Contains the lab infrastructure plus your existing containers
Prometheus Separate outer container Scrapes four Docker engines, two routed web services, and itself
Grafana Separate outer container Provisioned Prometheus data source and live lab dashboard

Each nested engine has its own /var/lib/docker volume. The managers and workers use separate bridge networks per Swarm for their underlay. Managers also join the access network for SSH and monitoring. Worker SSH servers are not started. The Docker API listens on Unix sockets, not a published unauthenticated TCP port.

Open the applications¶

All published ports bind to host loopback:

Application URL / port
Declarack custom page http://127.0.0.1:9080/#/~pages/lab
Declarack environments http://127.0.0.1:9080/#/environments
Grafana live dashboard http://127.0.0.1:9300/d/declarack-lab
Prometheus targets http://127.0.0.1:9090/targets
Swarm A application http://127.0.0.1:18081/health
Swarm B application http://127.0.0.1:18082/health
Manager A SSH 127.0.0.1:2221
Manager B SSH 127.0.0.1:2222

Declarack username is admin. Retrieve its generated password locally:

cat examples/multi-environment/runtime/declarack_password

Grafana permits anonymous Viewer access for this local lab. To administer it, log in as admin with runtime/grafana_password. Prometheus is unauthenticated inside the lab. Keep the loopback bindings when using these settings.

Ports can be overridden with exported environment variables before every lab command: LAB_DECLARACK_PORT, LAB_GRAFANA_PORT, LAB_PROMETHEUS_PORT, LAB_SSH_A_PORT, LAB_SSH_B_PORT, LAB_WEB_A_PORT, and LAB_WEB_B_PORT. Defaults are those in the table. Changing published ports on an existing lab needs up, not just configure. The primary app already running on port 8080 is unaffected.

SSH from your host¶

Keys are generated locally under the ignored runtime/ directory. SSH host keys are read from each manager through Docker and recorded in a dedicated known-hosts file; host verification stays enabled. Your personal SSH config/keys/known-hosts files are not changed.

ssh -F /dev/null \
  -i examples/multi-environment/runtime/client_key \
  -o UserKnownHostsFile=examples/multi-environment/runtime/known_hosts \
  -o StrictHostKeyChecking=yes \
  -p 2221 root@127.0.0.1

Use port 2222 for manager B. Inside either manager:

docker node ls
docker service ls
docker service ps lab-web
docker info

Only manager SSH ports are published. Declarack reaches workers through the manager API and node-pinned Swarm jobs, including volume inventory and terminals. The Declarack job image is loaded into every nested engine so these operations do not depend on GHCR credentials or an external registry.

Direct HTTP versus SSH tunnels¶

Both monitoring containers are reachable from either manager's access network. The default Declarack configuration uses manager A as the SSH hop for Prometheus and manager B for Grafana. Docker manager targets always use SSH; the host target uses the mounted socket.

Switch just the monitoring targets to direct container-network HTTP:

python3 examples/multi-environment/lab.py configure --http-mode direct
python3 examples/multi-environment/lab.py verify

Switch back to SSH:

python3 examples/multi-environment/lab.py configure --http-mode ssh
python3 examples/multi-environment/lab.py verify

configure recreates the runtime base config from the checked-in template and updates only Declarack. It overwrites local runtime config edits; copy your custom version elsewhere before regeneration. The Swarms, workloads, and monitoring keep running.

An HTTP target's optional tunnel block is:

grafana:
  connection: http
  base_url: http://grafana:3000
  ssh_tunnel:
    host: swarm-b-manager
    user: root
    identity_file: /run/lab/client_key
    known_hosts_file: /run/lab/known_hosts
    remote_host: grafana
    remote_port: 3000
  features: [grafana.dashboards]

Omit ssh_tunnel for direct access. The remote destination is resolved/reached from the SSH manager; the URL host remains the HTTP Host/TLS identity. The backend opens private Unix listening sockets and supervises the forwards. No local TCP forwarding ports need to be published for Declarack's internal tunnels. HTTPS verification, redirect restrictions, and the existing HTTPS requirement for bearer tokens remain. SSH encrypts to the manager; HTTPS is needed when the onward hop also needs TLS.

You can also create browser-facing forwards from your host's terminal. For Grafana through manager A:

ssh -F /dev/null -N \
  -i examples/multi-environment/runtime/client_key \
  -o UserKnownHostsFile=examples/multi-environment/runtime/known_hosts \
  -o StrictHostKeyChecking=yes \
  -L 127.0.0.1:19300:grafana:3000 -p 2221 root@127.0.0.1

Then open http://127.0.0.1:19300. For Prometheus, use -L 127.0.0.1:19090:prometheus:9090 and open http://127.0.0.1:19090. Either manager (2221 or 2222) can forward either service. Stop the SSH command with Ctrl-C. These user-managed browser forwards are separate from Declarack's managed internal tunnels.

Configuration files¶

  • declarack.yaml: complete checked-in config for all five targets, existing monitoring features, and a cross-target custom page.
  • runtime/declarack.ssh.yaml: generated container config with managed HTTP tunnels.
  • runtime/declarack.direct.yaml: generated container config with direct HTTP.
  • runtime/declarack.yaml: merged single-file copy of the selected transport.
  • runtime/config/: five ordered YAML base fragments, loaded by the container. Extra user fragments are retained by regeneration; base fragments are rewritten.
  • runtime/declarack.host.yaml: generated variant for running the Python backend on your host, with loopback SSH ports and absolute key/password paths.

The host-side variant can be used with DECLARACK_CONFIG and a different PORT; it does not require shutting down the lab's Declarack container. Its data directory is selected separately with DECLARACK_DATA. Never commit runtime credentials. Settings can browse the individual files and merged config, then explicitly reload external edits. Folder GUI writes are not enabled yet. Try the optional Grafana extension by copying one fragment into this folder and reloading.

Verify and stop¶

python3 examples/multi-environment/lab.py verify
python3 examples/multi-environment/lab.py status
python3 examples/multi-environment/lab.py down

Verification checks host SSH, distinct Swarm IDs, exactly one ready manager and worker per cluster, service replica convergence, each cluster's HTTP workload, all seven Prometheus scrapes, Grafana dashboard inventory, and the host Docker inventory through Declarack. It does not treat an HTTP 200 from Declarack alone as proof that every environment works.

down removes only this Compose project's containers/networks and retains its named volumes and local runtime credentials. Your existing host containers and Swarm membership are unaffected. A destructive reset is a separate explicit operator action: remove only the declarack-lab volumes after stopping, and remove its runtime directory if you want new client credentials. Keeping Grafana's data volume preserves its existing admin password, so keep its password file with it.

Node-local volume jobs were verified on both nodes of each Swarm. An interactive terminal into a worker task was also verified through manager SSH and the Swarm relay network. This is a real multi-node DinD test; independent physical-machine validation is still a separate deployment concern.

Environment groups and persisted monitoring¶

The generated folder includes 60-environments.yaml and 70-checks.yaml. Environment groups collect the two Swarms, local Docker, and monitoring targets. The top-level Targets page remains the complete connection inventory. Checks run on the server and keep their state/history in the existing Declarack data volume.

For a check-only target without an environment or interactive features:

cp examples/multi-environment/optional/checks.yaml \
   examples/multi-environment/runtime/config/75-monitoring-checks.yaml

In Settings, reload configuration, then open Checks. The optional check queries Grafana's real /api/health endpoint and evaluates database = "ok" with JSONata. See monitoring documentation for persistence, thresholds, single-replica deployment, and the current local-only alarm scope.

Optional volume browsing and SSH fleet pages¶

optional/tools.yaml adds two SSH host targets and batch pages for on-demand metrics and reviewed commands. Copy it into runtime/config/80-tools.yaml and reload. SSH metrics require Python 3 on those hosts; new lab engine builds include it. The standalone Docker override points volume helpers to declarack-lab:local. See volume/fleet documentation.

Environment-only custom pages¶

Copy optional/environment-pages.yaml into runtime/config/85-page-placement.yaml and reload Settings to add Local engine overview only within Local Docker. It is excluded from the global Custom pages section. The existing lab overview remains global and linked in the Swarm groups, demonstrating shared placement.

Root and fleet navigation¶

Home is the reserved environments.root. Configure its navigation to order or hide installation-wide links. Custom page placement uses environment pages lists; set root pages explicitly when a dashboard should appear only elsewhere. The optional SSH tools are assigned to ssh-hosts.batches and infer their hosts from that environment's targets, rather than repeating a host list in each tool. Open the SSH hosts environment to select hosts and collect metrics or confirm a fleet command. See navigation configuration.
