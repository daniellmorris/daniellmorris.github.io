Configure Declarack¶

Produce a configuration that matches the user's installed Declarack version and actual targets, with clear prerequisites and a verified save/apply workflow. This file is a portable agent instruction document: ask an assistant to read it before setting up configuration. It does not require a particular AI product. If a skill loader requires a directory entrypoint, copy this file into that skill's SKILL.md; keep its frontmatter and instructions together.

Configuration authority¶

The database holds saved and active configuration revisions. Files seed an empty installation; later external edits require explicit import or startup DECLARACK_CONFIG_FORCE_LOAD=1. GUI save and activation are separate. Optional DECLARACK_CONFIG_WRITE_BACK=1 publishes local files before activation; otherwise GUI edits do not change import files. Both flags default to off. Use the current storage contract for source imports, publication, recovery and backup requirements.

Credentials¶

Use top-level credentials profiles for all runtime credentials, including file references. Targets/tunnels select credential; registries map hostnames to basic profile IDs; Git uses an allowed ID list. Do not emit removed target fields identity_file, known_hosts_file, user, bearer_token_file, or target-local credential objects. See the schema.

Locate the relevant references¶

When a checkout is available, use its maintained files and adapter definitions. Otherwise use the linked repository references, matching the installed release rather than assuming main matches an older installation. If the files cannot be accessed, request the relevant configuration/schema instead of inventing fields.

Establish the inputs¶

Inspect an existing config before proposing a replacement. Determine the intended connections, target IDs, enabled capabilities, environment/page placement and storage source. For an HTTP integration, obtain representative JSON responses and verified methods/paths for reads and actions. Identify container-visible socket, source, credential and SSH known-hosts paths; a host path is not automatically available inside Declarack.

Reuse supplied values and existing IDs. Ask for missing facts that affect correctness; for illustrative output, mark assumptions and placeholders plainly. Do not fetch credentials from unrelated accounts or treat example endpoints as real deployment destinations. Stay within the user's requested setup scope.

Choose the configuration layer¶

  • Deployment/bootstrap: container mounts, Docker socket, environment variables, Docker secrets, selected config path and data-volume persistence.
  • System YAML: targets, operations, features, environments, pages, checks, batches, integration_templates and optional installation auth. At least one target is required.
  • Application source: a managed application's Compose YAML and its saved stack/project source. This is different from Declarack's own system config.
  • Runtime state: saved application-source metadata, checks, operation history and configuration revisions. Persist the selected database for those features (SQLite by default, or PostgreSQL).

Prefer a configuration folder for editable installations. DECLARACK_CONFIG selects one file or a recursively merged folder. Every fragment needs its root section wrapper; filenames do not imply sections. Visible .yaml/.yml files merge in case-sensitive relative-path order. Mappings merge recursively; lists, scalars and different types replace earlier values. Lists do not append. Duplicate keys within a YAML document are rejected. There is no include syntax, deletion marker or automatic environment interpolation in system YAML.

Use numbered filenames and dependencies from the snippet catalog as a starting point. When overriding an existing list, supply the complete desired list. Do not concatenate examples that repeat root keys into one document; keep separate files or explicitly merge their mappings. Do not point the application at the entire example catalog: it contains alternative configurations and incomplete fragments.

Assemble targets and presentation¶

  1. Choose the supported connection: docker_socket for Docker/Swarm, ssh for host operations, or http for an upstream API. Explicit Docker targets use swarm: true or false to choose mode. Inspect built-in YAML for feature IDs available on that provider. Docker standalone has no native Swarm configs/secrets.
  2. Reuse built-in features before defining custom ones. A custom feature names an inventory operation, JSONata rows/columns and optional details/forms/actions; the target enables it in its features list. Custom IDs must not collide with built-ins. New execution mechanisms require adapter work, not invented YAML.
  3. An operation selects a registered executor in a provider binding, with declared inputs and execution definitions. Feature/action bindings pass inputs to named operations. Use the installed schema for allowed request fields and validation.
  4. Environments group target IDs; they do not own the targets' feature definitions. Explicit grouping can leave check-only targets outside environment navigation. Settings and auth remain top-level. Navigation visibility is not authorization.
  5. A custom page defines named sources referring to enabled read operations on specific targets. Page expressions receive data.<source-name> results; feature expressions receive that feature's result/rows. Inspect actual response envelopes before mapping. Action-only operations cannot become page read sources.
  6. Place pages through environments.<id>.pages; set environments.root.pages explicitly to control home placement. top_level is no longer supported. On-demand/manual sources remain explicit collection actions; opening a dashboard should not silently launch node metrics.

Minimal HTTP integration example¶

This is a complete system-config example assuming GET /items returns {"items":[{"id":"one","name":"Example","status":"running"}]}. Replace the reserved .invalid address with the real API. No connection is tested by this example, and it adds no writes or scheduled work.

targets:
  example_api:
    label: Example API
    connection: http
    base_url: https://api.example.invalid
    features: [example.items]
operations:
  example.items.list:
    bindings:
      http:
        executor: http.request
        path: /items
features:
  example.items:
    title: Items
    group: Applications
    operation: example.items.list
    rows: items
    columns:
      - {label: Name, value: name}
      - label: Status
        value: status
        badges: {running: active, stopped: muted}
environments:
  example:
    label: Example environment
    targets: [example_api]
pages:
  example-summary:
    title: Example summary
    sources:
      inventory:
        target: example_api
        operation: example.items.list
    cards:
      - label: Items
        value: $count(data.inventory.items)

Read the linked workflow and page guides before extending this with forms, mutations, related resources, bulk actions or dynamic lookup operations. Add confirmed actions with appropriate labels/icons only for verified API behavior.

Credentials, scheduling and Swarm scope¶

Prefer credential references to mounted files or Docker secrets. Basic auth is installation-wide; supported Docker targets have separate registry_credentials and git_credentials mappings. Git access and image-registry access are distinct. Registry profiles match image hostnames; Git profiles match host and transport. Select a configured Git profile in the Swarm stack editor. Read the source guide for persistence and current Git/Compose limitations rather than assuming parity between source modes.

For SSH, mount the identity and known-hosts files. Swarm uses a manager socket or manager tunnel and short-lived jobs for worker-local work; it never SSHs into workers. Downloaded repository files do not provision bind-mount paths on workers.

Add checks only when scheduled behavior is requested. A check refers to a target and optionally an eligible read/check-safe operation, with healthy JSONata, interval and failure/recovery thresholds. A connector check omits the operation. Loading/reloading checks starts their schedules; results need persistent storage. Checks are not automatic GitOps deployment or a complete notification-routing system. Batches expose explicit multi-target operations; use the batch schema for inputs, results and confirmations rather than inventing a per-target loop in JSX.

Validate and apply¶

Validate the complete merged config, not just each fragment's YAML syntax. In a checkout with dependencies installed, a non-applying validation can use:

.venv/bin/python - /path/to/config-or-folder <<'PY'
import sys
from pathlib import Path
from backend.server import load_dashboard
config = load_dashboard(Path(sys.argv[1]))
print(f"Valid configuration: {len(config.targets)} targets")
PY

Use an environment with the required mounted files for configurations that refer to credentials or SSH identities. Report missing paths rather than bypassing validation. Schema validation does not prove connection reachability or JSONata mapping correctness against real responses; verify those separately with read operations and sample data. For catalog edits, run python -m unittest backend.tests.test_configuration_snippets in the project Python environment. Do not start a full application test suite for ordinary operator YAML edits unless its scope makes that useful.

In an editable folder installation, a writable config mount and DECLARACK_CONFIG_EDIT=1 enable GUI edits and new files. Use Review & save file or Review new file to validate and inspect source/effective merged diffs, then Save file. Reload configuration separately applies the saved source. Test all connections checks reachability without saving or applying. Auth and legacy-workspace changes can require restart. Local history restores one file to a draft, not an atomic whole-folder rollback. Single-file, Git-backed and Swarm-config-backed stores have different edit/publication limits; use the installed provider's documented flow.

Return the exact filenames/YAML or minimal patch, required mounts/credential references, validated assumptions and steps to apply. State what was actually validated, which connections were tested, and whether changes were only drafted, saved or applied. Preserve existing unrelated definitions and runtime workloads.
