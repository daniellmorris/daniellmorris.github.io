Declarack adapter architecture¶

For the implemented configuration schema and operational behavior, see the system configuration guide. The main YAML configures the system, including its dashboard presentation. This architecture document also contains adoption goals; the guide distinguishes those from current behavior.

Declarack is a configurable administration framework with Docker Swarm as its first full application. The same Python backend and React frontend can connect to a standalone Docker engine, an SSH host, or a generic upstream HTTP API. Adapters ship in the same production image. The dashboard can discover additional adapter packages from an operator-mounted directory when it starts.

Repository layout¶

  • backend/ contains the Python application, built-in adapters and their YAML definitions, the worker entry point, and backend tests.
  • frontend/ contains the React renderer, shared workflow controls, styles, and Vite package files.
  • The repository root contains deployment files, dependencies for the Python backend, and example configuration.

What goes where¶

Layer Owns
Core Authentication, configuration loading, target resolution, operation validation and dispatch, and consistent results and errors
Adapters Connections and reusable execution behavior such as Docker socket requests, SSH commands, HTTP requests, and short-lived Swarm jobs
Operation definitions Named calls, typed arguments, request or command configuration, result format, and supported execution scopes
Feature definitions Navigation, routes, tables, forms, metrics cards, actions, and JSONata display mappings
Deployment configuration Config storage selection, target addresses, enabled features, adapter directory, and references to mounted credentials

An adapter implements a reusable mechanism. Adding a new list or inspect operation that uses an existing mechanism usually means adding configuration. Adding a new connection type or a workflow that needs coordination means adding adapter code.

Adapter discovery¶

Each adapter occupies one directory with a manifest and a Python entry point. The image includes the built-in packages under /app/backend/adapters. Operators can mount an optional read-only directory at /etc/declarack/adapters for additional packages.

adapters/
  docker/
    adapter.yaml
    adapter.py
  swarm/
    adapter.yaml
    adapter.py
  ssh/
    adapter.yaml
    adapter.py
  http/
    adapter.yaml
    adapter.py

Example manifest for the Swarm adapter:

id: swarm
api_version: 1
entrypoint: adapter.py:register
depends_on: [docker]

At startup, the core reads the manifests, checks their IDs and interface versions, then loads adapters in dependency order. Each entry point registers the connection types and execution methods it supplies, along with schemas for their configuration. The core validates the target, operation, and feature definitions against that registry before serving the application. Duplicate IDs, missing dependencies, unsupported versions, and unknown references are startup errors that name the affected package or config entry.

An adapter can also bundle operation and feature definitions. Its manifest lists those files by path relative to the package directory. Discovery makes the definitions available, and the installation config chooses which features to enable on each target. A package that registers only a connection or executor can be used by definitions supplied elsewhere in the deployment.

To add an adapter, put its directory under one of the discovery roots, make its dependencies available in the image if it has any, reference its registered connection or execution method in config, and restart the dashboard. The core and generic UI renderer require no changes. Feature definitions can use the shared UI components. A bespoke React page still needs a frontend build.

Adapter Python runs inside the dashboard process with its credentials and connection permissions. Treat an adapter directory like application code and restrict who can modify it. The Settings UI edits supported target settings. Top-level operation, feature, authentication, and legacy-workspace changes happen through deployment; see the configuration guide for the exact restriction. Adapter installation also happens through deployment.

The initial implementation includes Docker socket, Swarm node jobs, SSH, and HTTP adapters. Stack, config, and secret views use the same renderer as other features. Use legacy_workspace to associate an existing database and bookmarks with one configured Swarm target. See README.md for deployment switches.

Connections and operations¶

A target defines where a request goes. An operation defines what happens there. The names a feature invokes exist only when the loaded operation definitions register them.

targets:
  production:
    connection: docker_socket
    socket: /var/run/docker.sock
    swarm: true
    agent_image: registry.example.com/declarack:0.3
    features:
    - services
    - volumes
    - host_metrics
  lab:
    connection: docker_socket
    socket: /run/docker-lab.sock
    features:
    - volumes
    - networks
  backup:
    connection: ssh
    host: backup.example.com
    features:
    - host_metrics
    credential: ssh_backup
  inventory:
    connection: http
    base_url: https://inventory.example.com
    features:
    - asset_inventory
    credential: token_inventory
auth:
  provider: local
  bootstrap_credential: declarack_login
  session_hours: 8
credentials:
  ssh_backup:
    type: ssh
    username: dashboard
    private_key:
      file: /run/secrets/backup_ssh_key
    known_hosts:
      file: /etc/declarack/known_hosts
  token_inventory:
    type: token
    token:
      file: /run/secrets/inventory_token
  declarack_login:
    type: basic
    username: admin
    password:
      file: /run/secrets/declarack_admin_password

An operation can have more than one binding. Here, volumes.list uses a node-local collector on Swarm and an engine request on standalone Docker.

# operations/volumes.yaml
operations:
  volumes.list:
    bindings:
      docker_swarm:
        executor: swarm.exec
        inputs:
          node_id: {type: string}
        all_nodes: true
        command: [python, -m, backend.adapters.docker.node_agent, volumes]
        mount_profile: docker_socket
        output: agent_json
      docker_standalone:
        executor: docker.volumes
        operation: volumes

A Docker socket target with swarm: true selects the docker_swarm binding and must reach a manager. Other Docker socket targets select docker_standalone. An operation call identifies the target, the operation, and its declared inputs. The core selects the matching binding before dispatch.

An upstream integration can use the same model with an HTTP target and a request binding. The trusted config supplies the origin, credentials, method, and route. Calls supply typed values for declared fields. Request runners encode path segments and query values. Command runners pass declared arguments to the configured executable. SSH verifies host keys and quotes remote command arguments. The dashboard does not forward credentials across HTTP redirects to a different origin.

Multiple bindings for an operation should expose a documented shared result shape. The volume collectors return name, driver, and local container attachments on both targets. Swarm adds node identity. All-node results wrap the individual responses so the view can report partial failures.

Swarm behavior¶

Swarm uses the manager's Docker socket for all cluster access. An inspect operation is a direct request. An exec operation scoped to a Swarm node uses the same connection to start a short-lived job pinned to that node. The job runs from the dashboard image, emits structured output to stdout, and exits. The manager reads the task logs and removes the job. Worker operations have no SSH fallback or network callback.

An explicit All nodes request takes a snapshot of the selected nodes and fans out with bounded concurrency. The runner returns one result or error per node, including unavailable nodes. The feature can flatten successful results into a table or calculate a summary while showing how many nodes reported. Volume writes stay scoped to one node. If a write times out and its outcome is uncertain, refresh the affected node's state before retrying.

Keep coordination in reusable code. Swarm owns job placement and cleanup, version-aware service and node updates, and stack deployment through the manager. Simple inventory requests belong in operation config. Stack workflows can call code for Git checkout, preview validation, and deployment.

Views, state, and settings¶

Feature definitions tie operations to routes and shared UI components. For example, Volumes declares an inventory table, a node selector on Swarm, and create and remove actions. JSONata can transform rows or compute totals. Resource IDs, action inputs, and authorization remain independently validated by the backend. Details and creation forms retain their own URLs.

Metrics are on demand for every target. Opening a view launches no collector. An explicit request can sample counters briefly and return one snapshot. Keep snapshots in memory with their timestamps. Swarm and SSH can expose the same host metrics page by returning the same fields.

The database owns the saved and active system configuration revisions. Files, folders, Git and Swarm configs supply import/publication sources. Sources seed an empty database; subsequent startup loads its active revision unless DECLARACK_CONFIG_FORCE_LOAD=1. Local DECLARACK_CONFIG_WRITE_BACK=1 publishes documents with recovery journaling before activation. See configuration storage. Source providers retain these publication mechanisms:

Storage Apply behavior
Mounted file Atomically replace a validated file and retain the previous revision
Git Open a pull request and apply the merged revision through deployment
Swarm config Create a versioned config and update the dashboard service to mount it at the same path

Validate the expected revision before saving. Prefer mounted secrets for credential values; inline profile values also persist in configuration history and exports. A Swarm config can reference an already mounted secret for first-administrator bootstrap. Swarm config storage manages the system configuration, not all application state. GUI-managed sources, legacy encrypted PATs/keys, checks and history use the shared SQLAlchemy persistence service: SQLite by default or PostgreSQL. Adapters use namespaced documents; Compose inline files are reconstructed locally. Persist the selected database. See storage for explicit upgrade/import and execution boundaries. A fully stateless source-management mode remains an architectural goal.

Adoption¶

  1. Introduce the adapter registry and extract Networks as the first configured feature. Prove the same network view works on a Swarm manager and a standalone Docker engine.
  2. Extract Volumes and Host Metrics. Verify direct engine calls, node-pinned jobs, explicit fan-out, and SSH collection with a shared metrics response. Confirm that opening a metrics page launches no work.
  3. Migrate the remaining Swarm features and prove a generic upstream HTTP integration by adding its adapter and config without changing core code. Preserve the existing single-manager setup and bookmarks during the migration.
  4. Add the Settings storage adapters and test config conflicts, reload, rollback, and mounted-secret authentication. Run live smoke tests with a Swarm manager and worker, a standalone engine, and a Linux SSH host. Measure the production image against the 50 MB compressed target.

Current implementation boundaries¶

The application composition in backend/server.py installs settings, operation and check endpoints, static assets and the backend/auth/http.py cookie/CSRF boundary. backend/auth/store.py owns database administrators, bootstrap, password hashes, sessions and login limits. backend/serving.py owns the Cheroot listener, native TLS and explicit immediate-proxy trust. Docker/Swarm services are grouped under backend/adapters/docker/ and backend/adapters/swarm/. The runtime module composes those services, and legacy_routes.py adapts old URLs to them. Node helper commands live in backend/adapters/docker/node_agent.py. Adapters do not call back into the HTTP server to perform resource operations.

Resource selectors map lookup responses through JSONata. Terminal fields come from operation input schemas, while backend/terminal_sessions.py manages bounded PTY sessions with adapter-supplied commands and ownership scopes. Docker exec, Swarm worker relays and SSH host sessions implement that same contract. File views consume a file-tree response with provider-advertised limits; adapters choose the root and execution location. String identifier constraints and navigation icons are explicit configuration rather than resource-name branches in core.

See generic capabilities for schemas and the pre-release configuration changes.

See code organization and development checks for module responsibilities and the contributor verification commands.

Installation identity and transport¶

Local database administrators are independent of target credential profiles and YAML configuration revisions. auth.provider is local; an optional bootstrap_credential basic profile seeds only the first account when no users exist. Otherwise bootstrap uses DECLARACK_ADMIN_USERNAME and a password file or environment value. Existing accounts ignore subsequent bootstrap secret changes. session_hours defaults to 8 (1–168). All administrators have full installation, credential and workload access; environment grouping is not a permission boundary. There are no granular roles, teams or SSO, and HTTP Basic Auth is unsupported.

Passwords use scrypt hashes; opaque session tokens are stored as hashes in the database. The HTTP layer requires cookies and action/CSRF headers for authenticated writes. Cookies are HttpOnly/SameSite=Lax and Secure when HTTPS is observed. Account writes revalidate the actual session hash under the database account lock after password hashing, so revoked sessions cannot finish queued account writes. Account mutations record secret-free events in generic documents under framework.auth.audit (newest 1,000 retained; activity API returns newest 100). Actors identify the administrator or bootstrap/host operator. Operation-plan metadata.actor records request identity, preserved through ContextVar propagation in batch fan-out. Bounded account events and plan metadata are not a complete generic resource audit log; direct calls do not all produce recorded plans. Demo bypasses login and does not expose account management.

Native TLS accepts mounted PEM files or persisted self-signed identity under <DECLARACK_DATA>/tls; it is separate from database transfer. There is one listener, startup-only certificate loading, and no ACME, automatic renewal or redirect listener. Explicit trusted proxy IPs/CIDRs permit one forwarded proto/client hop, never forwarded host/prefix. See administrators, recovery and TLS.
