Concepts and terminology¶

Declarack turns a system configuration into an administration interface. YAML chooses connections, operations and views; JSONata maps returned data. Adapters supply execution mechanisms and resource-specific rules.

Start with How configuration fits together for diagrams, a complete example and the edit/review/save/reload workflow.

The configuration model¶

Term Meaning Example
Target A configured connection A Docker socket, Swarm manager, SSH host or HTTP API
Environment A group of target references with navigation placement Production contains its Swarm, monitoring API and SSH hosts
Operation A named request or command with an input schema List applications or restart a selected service
Binding How an operation runs for a provider An HTTP request or Docker API call
Feature A resource view plus its actions/workflows Containers, applications or dashboard inventory
Page A custom layout combining read sources Cards and charts across multiple targets
Workflow A config-defined form and action sequence in the UI Collect inputs, preview changes, confirm and execute
Check A scheduled connection or read-operation evaluation API readiness every 30 seconds
Adapter Trusted code and YAML discovered from a folder Docker, Swarm, SSH or HTTP
Integration template A starting configuration expanded from form values Add a second Grafana instance

An environment organizes targets. It is not a transport or an authorization boundary, and targets can belong to multiple groups or none. Features belong to targets. The reserved root environment is Home; it is not an inheritance parent. Pages and fleet tools are placed through environment membership lists, including root. Page sources explicitly name targets and are independent of page placement.

What the YAML controls¶

targets: {}                 # At least one connection
environments: {}            # Groups; explicit empty leaves only reserved root
operations: {}              # Named requests/commands
features: {}                # Resource views and actions
pages: {}                   # Multi-source layouts
checks: {}                  # Scheduled evaluations
batches: {}                 # Configured multi-target operation pages
integration_templates: {}   # Additional trusted setup presets
# auth: ...                # Installation-wide authentication

The system configuration is broader than a dashboard layout. It does not replace a Compose file, Docker's daemon settings or application deployment source. Enabling a feature does not deploy an application.

A request through the framework¶

  1. An enabled feature invokes a named operation on a target.
  2. The backend validates the operation's declared inputs and selects its provider binding.
  3. An adapter executes the request, command or node job.
  4. JSONata maps the response into rows, fields, cards or chart points.
  5. The shared renderer presents the result and its configured actions.

Docker/Swarm details remain in adapters and their YAML. The UI does not need a new resource-specific component for each external API.

State and execution¶

The active database revision defines behavior; its documents retain the YAML schema. The shared database stores saved source records, legacy encrypted credentials, check history, operation runs and configuration revisions. SQLite under the data directory is the default; PostgreSQL is optional. Local checkouts, materialized Compose files and other transient working files still use the data directory. YAML files seed or explicitly update database configuration. Only one active controller is supported. Browser preferences such as density/page size are separate. Charts do not retain time-series samples.

Most reads run on demand or when opening a view. Browser auto-refresh is opt-in; scheduled checks run in the controller process even when the browser is closed. A server-owned operation plan continues after its browser closes, but an interrupted backend does not automatically resume that plan.
