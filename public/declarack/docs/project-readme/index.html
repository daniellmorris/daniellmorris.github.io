Declarack¶

Connections select reusable credential profiles, managed through Settings → Credentials. Paste/upload a value or reference a mounted file; both use the same named configuration model.

Configuration is database-managed: files seed the first startup, GUI edits are reviewed and saved, and Activate configuration makes a saved revision active. Optional DECLARACK_CONFIG_FORCE_LOAD=1 imports files at each startup; DECLARACK_CONFIG_WRITE_BACK=1 writes them before GUI activation. Both default to off. See storage and configuration ownership.

Administration interfaces, defined in configuration.

Declarack turns connections, operations, and YAML definitions into a working admin interface: searchable tables, dedicated detail pages, forms, confirmed actions, terminals, and environment summaries. Start with Docker and Swarm management, then bring your own HTTP APIs or SSH hosts into the same workspace.

Manage a homelab, operate a small Swarm, or assemble an internal administration portal without writing a new frontend for every integration.

  • One view across environments. See configured systems together, or define custom pages that query multiple targets and combine their results with JSONata, including charts, filterable tables and opt-in refresh.
  • Useful Docker management from day one. Manage Compose projects and Swarm stacks; inspect resources, read logs, open container terminals, and clean up storage. Edit or duplicate standalone containers with reviewed plans and retained backups.
  • Configuration-driven extensions. Define API operations, map results with JSONata, and reuse views and workflows across environments.
  • A small, modular core. Python backend, React UI, folder-discovered adapters, and on-demand node work. Swarm workers are reached through jobs, not SSH.

Documentation¶

Read the quickstart, follow the runnable API interface tutorial, or browse the configuration reference. To preview the complete searchable documentation website locally, see documentation development.

Start with a configuration¶

Already running with a writable configuration folder? Open Targets → Add integration to generate and review a Docker, Swarm, SSH, Grafana, Prometheus or HTTP API configuration. Save it as a new YAML fragment, then reload.

Your use case Included starting point
Standalone Docker / Compose apps Docker management
Swarm services, stacks, and nodes Swarm management
A custom page across Docker, Swarm, and monitoring Operations dashboard
Local Docker plus a remote Swarm Multiple environments
Linux host metrics SSH host
Existing target health and alerts Prometheus
Existing dashboard inventory Grafana
Your own application API Complete custom application example

Docker/Swarm presets include management actions. Prometheus/Grafana presets are read-only integrations with existing services. See the configuration catalog for connection requirements, API/version notes, and instructions for combining them. The Docker image includes these presets at /app/configurations.

Try the complete multi-environment lab¶

Run the real Docker-in-Docker lab: two Swarms with one manager and one worker each, running services, Grafana, Prometheus, and your host Docker engine, connected through direct access or SSH tunnels.

python3 examples/multi-environment/lab.py up --http-mode ssh

The lab GUI uses port 9080 and keeps the normal port-8080 installation separate. See the lab guide for generated credentials, host SSH commands, transport choices, and the complete five-target Declarack configuration.

Run locally¶

From a checkout with Docker available:

export DECLARACK_PASSWORD='replace-with-a-strong-password'
docker compose up -d --build

Open Declarack and sign in as admin on the login page. The password seeds the first database administrator only; later environment changes do not rotate that account. Manage accounts under Settings → Administrators. The default setup detects a local Swarm manager or standalone Docker engine. To choose an explicit configuration, follow the catalog setup. No Docker/Swarm experience is required to configure an HTTP API integration, but you do need a reachable API and knowledge of its response shape.

The Compose service publishes to loopback and persists saved sources/credentials in its declarack-data volume. For remote access, use an SSH tunnel or a trusted HTTPS reverse proxy, or configure native TLS. See administrators, password recovery and TLS for bootstrap files, session/CSRF clients, certificate persistence and proxy trust. All administrators have full installation access. Docker socket access gives Declarack administrative control of the connected engine. Keep its data volume private and back it up.

Set DECLARACK_STACKS_DIR to a host directory for local stack sources; Compose mounts it read-only at /stacks. Use DOCKER_SOCKET for an alternate socket when running Python directly, and mount/select that socket explicitly in container deployments.

Make it your administration interface¶

The system configuration controls environments, enabled capabilities, operation definitions, views, workflows, and authentication. It is broader than a dashboard layout. Existing adapters cover Docker, Swarm jobs, SSH, and HTTP; new execution mechanisms can be added as trusted adapter packages.

This is a configurable administration framework with Docker/Swarm as its most complete application. Config-defined charts and persisted scheduled checks are available. Visual chart builders, SSO/RBAC and outbound check notifications are not implemented; see health checks.

Upgrading from the previous product name? Read the rename guide before changing your Compose service or data-volume mapping.

Deploy stacks¶

  1. Open Stacks, create a stack or edit the source of an existing stack, and choose one source.
  2. Compose editor stores the YAML in Declarack.
  3. Mounted folder loads docker-compose.yml or docker-compose.yaml from a directory relative to the mounted source root. Enter . to use the root.
  4. Git repository (HTTPS / SSH) supports branches, tags and commit IDs across Git providers, with target-scoped credential references. See registry credentials and Git sources.
  5. GitHub tag loads the Compose path from an owner/repository and tag. For private repositories, enter a username and a PAT with read access to repository contents. Declarack stores the source metadata and encrypted PAT in its configured database. The Source page shows the saved repository, tag, Compose path, token status, and last deployed commit. A blank PAT retains the saved credential for the same repository and username. Clear the username to remove the saved credential.
  6. Save the source and preview it. For GitHub, the preview displays the exact commit. Use Validate to run docker stack config.
  7. Choose Deploy and confirm. Declarack checks the preview against the current Compose file and Git commit, then runs docker stack deploy. Check the stack’s service and task views while Swarm converges.

For an existing stack, choose Update in place to keep services absent from the reviewed file, Update and remove orphaned services to prune those services, or Replace stack to validate the Compose file, remove the deployed resources, and redeploy. Replace causes downtime and keeps volumes by default. Turn on Clear selected volumes during replacement to scan nodes and explicitly select volumes to delete. Only existing, stack-labeled local volumes referenced by the deployed services and declared under their default stack-scoped name in the reviewed source are eligible. External, shared-driver, and volumes attached to unrelated containers are excluded. Use the same updated image for Declarack and its node jobs. If the new deployment fails after removal, inspect the cluster and redeploy when the cause is resolved.

To tear down a deployed stack, open its Source page, choose Remove deployed stack, and confirm. Docker removes services and stack-owned networks, configs, and secrets. The saved source and volumes are retained. Preview and deploy the source to recreate the stack.

Deployments are manual. Updating a tag or a folder does not trigger a deployment. GitHub sources are bounded to 16 MiB compressed and 64 MiB extracted and support regular files and directories. Use stack files from trusted sources. Target-scoped registry credential files now support private image pulls, Compose up, Swarm stack deployment with worker authentication, and reviewed service edits. Bind mount paths in service definitions must exist on the target Swarm nodes.

Manage configs and secrets¶

Use Configs or Secrets to create a resource from pasted text or a file of up to 500 KiB. The GUI displays references from running service definitions. To rotate a config or secret, create a new version, update your Compose source to use it, redeploy, and remove the old version after it has no service references. Reference Swarm resources as external: true in Compose and keep secret values out of Compose files. Docker Swarm returns metadata and usage for secrets after creation.

The dashboard also supports scaling services, node scheduling changes, and recent logs. A standalone engine or worker can display local container data and logs.

Demo and development¶

For a backend-free playground, run npm run demo --prefix frontend after installing frontend dependencies. This serves the existing GUI with a browser-only simulated API. See static browser playground for free static hosting, supported workflows and limitations.

Run the demo directly from the production image:

docker build -t declarack .
docker run --rm -e DECLARACK_MODE=demo -p 127.0.0.1:8080:8080 declarack

The demo uses sample inventory and temporary data. For local development with Node 22.12+ and Python 3.12+, run:

npm --prefix frontend ci
npm --prefix frontend run build
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
DECLARACK_MODE=demo .venv/bin/python -m backend.server

A local Docker CLI enables Compose validation in the demo. Networks with a private CA can pass a host CA bundle to Docker BuildKit with --secret id=build_ca,src=/path/to/ca-bundle.crt. This only affects dependency installation during the build.

Node jobs, volumes, and host metrics¶

Build and publish this same image to a registry that the Swarm nodes can pull from. Set DECLARACK_AGENT_IMAGE to that image reference on the manager, preferably by digest. Use the same version for the dashboard and node jobs.

  • In Volumes, choose a node or all nodes and select Refresh volumes. Each result shows the node, volume driver, and local container attachments. Create a named local volume on a selected node or remove an unused volume. Docker enforces its own in-use checks. Removing a volume deletes its data.
  • To enable host metrics, set DECLARACK_HOST_METRICS=1 on the dashboard. Open Host metrics, select a node, and choose Collect to see CPU, memory, host disk, swap, network throughput, kernel, and uptime. Each snapshot shows its collection time. Disk capacity is measured on the filesystem containing /etc by default. Set DECLARACK_HOST_DISK_PATH to an absolute directory on a different node filesystem, such as the Docker data directory, to measure it instead.
  • Volume jobs mount the selected node’s Docker socket. If all worker sockets use an alternate path, set DECLARACK_WORKER_SOCKET to that host path. Metrics jobs use read-only Linux host mounts.
  • Jobs require a ready, active Linux node and a Docker Engine with support for replicated jobs. The manager pins each job by node ID, reads its JSON result via Docker task logs, and removes the job. A timed-out write can have an unknown outcome, so refresh the volume list before retrying. No inbound callback or persistent worker process is required.

Networks and detail pages¶

Networks lists Swarm overlays and networks known to the connected Docker engine. Open a network to see its scope, driver, IPAM subnets, Swarm service references, and endpoints reported by that engine. Worker-local network inventory and network creation or removal are outside this view.

Resource details and creation forms have their own URLs. Use the back link or your browser history to return to the inventory.

Configured targets and adapters¶

DECLARACK_CONFIG can point to one file or a folder. Folder YAML fragments merge into one system configuration; Settings can show each file and reload validated changes without rebuilding the application. Start with the folder example and merge/reload guide.

The main YAML is Declarack's system configuration: it controls connections, capabilities, execution definitions, UI presentation, and authentication. Read the complete configuration guide for schemas, examples, storage modes, edit restrictions, and runtime settings. A complete custom API example is included.

The original single-manager setup works without a config file. To use configured targets, start with dashboard.example.yaml, mount it as /etc/declarack/dashboard.yaml, and set DECLARACK_CONFIG=/etc/declarack/dashboard.yaml. Mount the sockets and credential files referenced by that config. Use auth: {provider: local, bootstrap_credential: login, session_hours: 8} with a named basic login profile referencing a mounted password file, or use DECLARACK_PASSWORD_FILE / DECLARACK_PASSWORD for first-account bootstrap. Existing provider: basic / credential configuration must migrate to local / bootstrap_credential; HTTP Basic Auth clients must use login cookies and CSRF/action headers. Accounts are stored separately from YAML.

The example enables standalone Docker. Add a Swarm manager, an SSH host, or an upstream HTTP API as another target. Swarm never uses SSH to reach workers. SSH host metrics require python3 on the remote Linux host and an OpenSSH-format identity readable by the dashboard. Enable stacks, configs, and secrets in each applicable Swarm target. The same YAML renderer serves configured targets and single-manager installs. Use legacy_workspace: <swarm-target-id> to associate pre-existing saved stacks and bookmark routes with that target. Other targets keep source records in separate logical database scopes. SQLite is the default; PostgreSQL is optional. See storage and migration.

The app discovers built-in adapters in /app/backend/adapters and additional packages in /etc/declarack/adapters or DECLARACK_ADAPTER_DIR. Mount additional adapters read-only and restart to load them. An adapter can register a connection, operation executor, and optional YAML files with operations and features. See the architecture writeup for the boundaries and the existing backend/adapters/ packages for the actual config schema.

Settings storage¶

Settings can validate supported target changes and test a target connection. Changes to top-level operations, features, authentication, or legacy-workspace settings currently require deployment and restart; see the configuration guide. Choose how supported edits apply:

  • File is the default. Set DECLARACK_CONFIG_EDIT=1 and mount the enclosing directory writable for atomic saves. The preceding revision is retained next to it with a .previous suffix.
  • Swarm uses DECLARACK_CONFIG_STORE=swarm and DECLARACK_CONFIG_SERVICE to select the dashboard service. The mount target defaults to DECLARACK_CONFIG and can be overridden with DECLARACK_CONFIG_MOUNT. The service update uses the manager socket, optionally overridden by DECLARACK_CONFIG_SOCKET. Docker service rollback can restore the prior config attachment while its config still exists.
  • GitHub uses DECLARACK_CONFIG_STORE=git with DECLARACK_CONFIG_GIT_REPO in owner/repo format. Set DECLARACK_CONFIG_GIT_BRANCH and DECLARACK_CONFIG_GIT_PATH as needed. DECLARACK_CONFIG_GIT_TOKEN_FILE is a mounted credential. Creating pull requests requires repository Contents and Pull Requests write access. The running dashboard still boots from the mounted file, so arrange for merged revisions to update that mount and restart or redeploy it.

Authentication provider/session configuration, adapter packages, and operation and feature definitions are deployment settings. They cannot be changed from the dashboard's Settings editor.

Run the adapter and storage tests with python -m unittest discover -s backend/tests after installing the Python dependencies.

Remote Docker over a managed SSH tunnel¶

For a remote manager, replace the target's socket setting with ssh_tunnel. The dashboard container starts OpenSSH as a subprocess when the connection is needed, keeps it alive, and reconnects after a failure. No host-side tunnel service or Docker TCP listener is required.

targets:
  production:
    connection: docker_socket
    swarm: true
    ssh_tunnel:
      host: swarm-manager.example.com
      remote_socket: /var/run/docker.sock
      credential: tunnel_production
    features:
    - overview
    - services
    - nodes
    - tasks
    - stacks
    - configs
    - secrets
    - networks
    - volumes
    - host_metrics
    agent_image: registry.example.com/declarack:0.3
    host_metrics: true
credentials:
  tunnel_production:
    type: ssh
    username: dashboard
    private_key:
      file: /run/secrets/production_ssh_key
    known_hosts:
      file: /etc/declarack/known_hosts

Mount the OpenSSH-format private key and a verified known_hosts file in the container. Set the private key mount to mode 0400 and make it readable by the dashboard process. The manager's SSH server must allow stream-local forwarding and the SSH account must be able to access the manager's Docker socket. A nonstandard SSH port can be set with port. The socket is private to the dashboard container. Use a separate target for each manager. Swarm reaches workers via the manager's Docker API.

Stack operations and the bundled Docker CLI use the selected manager connection too. The Swarm-backed Settings store still uses its deployment-side manager socket, configured separately with DECLARACK_CONFIG_SOCKET.

Docker actions and interactive terminals¶

See Docker GUI action coverage for the implemented action matrix, configuration examples, terminal behavior, and remaining CLI coverage.

Standalone Docker targets also expose Compose projects for discovery, saved inline/mounted sources, and reviewed lifecycle actions. Swarm task terminals use temporary node relay jobs when agent_image is configured. See the action coverage document for setup and constraints.

View existing Compose files from the host¶

Optionally mount the host filesystem read-only and expose reported Compose files:

# Native Linux Docker host:
docker compose -f compose.yaml -f compose.host-files.yaml up -d --build

# Docker Desktop on macOS (reported paths under /Users):
docker compose -f compose.yaml -f compose.host-files.macos.yaml up -d --build

These optional overrides set DECLARACK_COMPOSE_HOST_ROOT=/mnt/host. Native Linux mounts / there; the macOS override mounts /Users at /mnt/host/Users because Docker Desktop's / is the Linux VM filesystem. Narrower read-only binds work too when they preserve the reported absolute path beneath /mnt/host.

Open a Compose project and select View host Compose files. Missing, unreadable, non-regular or oversized files are reported individually. The viewer reads files; it does not save a deployment source or alter the project. A host-root mount grants the dashboard read access to the selected host paths, so it is opt-in.

For multiple targets, set each target's host_root to the matching mounted host filesystem. A local mount cannot expose a remote Docker host's files; SSH-tunnel targets require an explicit per-target mapping. When running the Python development server directly on the same host as the Compose source files, use DECLARACK_COMPOSE_HOST_ROOT=/ without a container bind mount.

Multi-environment dashboard¶

For custom pages with cross-target queries, shared JSONata context, cards, and tables, see the custom pages guide. The Environments page below remains the navigation view for individual targets.

The home page (#/environments) summarizes all configured targets. Each environment has its own snapshot, refresh button, feature links, and Open workspace action. Search by label, target ID, or provider. Existing target and resource bookmarks continue to work. Add environments under targets in the configured dashboard; this page does not discover or create remote connections automatically.

Standalone Docker summaries show Compose projects, total/running/not-running containers, and image counts when those features are enabled. Swarm overview summaries show services, ready nodes, stacks, and services below desired replicas. A failed summary is isolated to its environment; partial results remain usable. Loaded means summary requests succeeded, rather than a health guarantee. Targets without summary definitions still offer links into their workspaces, including SSH hosts whose metrics require manual collection.

Collection runs only on page entry or explicit refresh, with at most four requests in flight and a 15-second client timeout per request. Leaving the page cancels pending browser requests; it does not guarantee cancellation of work already started on a remote server. No host-metric or volume-inventory jobs are started by this dashboard.

Adapters and custom features opt in using the existing feature operation and JSONata expressions, for example:

features:
  asset_inventory:
    title: Assets
    operation: inventory.list
    rows: items
    columns: [{label: Name, value: name}]
    environment:
      cards:
        - {label: Assets, value: '$count(items)'}
        - label: Unhealthy
          value: '$count(items[healthy = false])'
          tone: '$count(items[healthy = false]) > 0 ? "destructive" : null'

Each card supports label, JSONata value, optional JSONata caption and tone, and an optional destination feature. Environment summaries must use operations without inputs and cannot be marked manual or on demand. Declare summaries only for inexpensive read operations. They inherit each target's enabled features and operation permissions; connection settings and credentials are not sent to the UI.

Configuration folders can be edited from Settings with full-merge validation, source and effective-config diffs, and local revision history. Save a reviewed file, then reload to apply it. Historical content restores into a draft for review. See configuration editing and recovery.

For AI-assisted setup, load CONFIG_SKILL.md: a portable guide for creating, validating and applying Declarack configuration. Contributors and coding agents should start with AGENTS.md.

Persistence defaults to a local SQLite database. PostgreSQL is available through a database URL or mounted URL secret. Existing installations need an explicit storage import; both backends currently support one active controller.
