Source-based forms and tracked operation plans¶

Declarack's core supplies reusable form controls, source mapping, reviewed actions, and durable operation records. Docker-specific recreation rules live in the Docker adapter, not the React renderer. This is the first built-in consumer of the plan runner; YAML does not yet provide an arbitrary background workflow language.

Structured form fields¶

Workflows support these field types in addition to ordinary inputs and JSON:

fields:
  - key: labels
    label: Labels
    type: key-value
    max_items: 100
  - key: env
    label: Environment
    type: string-list
  - key: ports
    label: Ports
    type: collection
    item_fields:
      - {key: port, label: Container port, type: number, integer: true, min: 1, max: 65535, required: true}
      - key: protocol
        label: Protocol
        type: select
        default: tcp
        choices: {tcp: TCP, udp: UDP}

Each control can switch between rows and advanced JSON. Maps reject duplicate or empty keys and non-string values. Collections retain unknown row properties, so editing known columns does not discard future API fields. Numbers, bounds, required columns and select choices are checked before requests are submitted. Operation schemas and adapter validation remain authoritative on the server. The default row limit is 256. A key-value field can specify key_pattern.

Swarm service labels, environment, commands and ports use these controls; Docker container forms reuse them. Advanced API structures remain available as JSON.

Seeding and dependent defaults¶

initial maps source fields into form fields. seed.expression selects the base object before initial mappings; seed.omit removes dot-separated paths from a copy. Without a seed expression, the source entry is the base as before.

seed:
  expression: config
  omit: [identity, metadata.version]
initial:
  source_id: Id
fields:
  - key: mode
    label: Operation
    type: select
    choices: {duplicate: Duplicate, replace: Replace}
    reset_map:
      name: 'form.mode = "duplicate" ? entry.editor.copy_name : entry.editor.name'
      start: 'form.mode = "replace" and entry.editor.running'
    changes_source: true

The selected value is already in form when reset_map runs. JSONata expressions also receive the usual workflow context. changes_source invalidates the preview. A feature can use workflow_by_provider to replace its workflow for a particular provider. All variants are validated; only the selected variant's operations are exposed for that target. This keeps standalone replacement off Swarm task pages.

Server-owned execution¶

Adapter executors can submit ordered Step instances to operation_runs() from the backend services dictionary. Each step has an ID, title, callable, optional condition and descriptive retry_safe flag. The runner records pending, running, completed, skipped and failed steps. If execution fails, it runs the explicitly declared recovery steps in order, attempting remaining recovery steps even when one fails. A retry-safe declaration does not cause automatic retries.

A workflow action consuming the resulting {run_id: ...} uses:

await_run: true
open_result: container_id

The browser follows the run through GET requests and opens the returned resource when complete. Closing the browser stops watching; execution continues on the server. The global Operations page lists recent runs and displays step results, recovery failures and metadata. APIs are GET /api/v1/runs and GET /api/v1/runs/<id> under the existing application authentication.

Records live in the shared database. Resource/run lock files remain local to the runtime data directory. Persist the database to retain records. The latest 1,000 terminal records are retained, and the list returns the latest 100. Step results are bounded at 128 KiB. A resource lock serializes plans against the same daemon/container, including aliases targeting the same engine; it does not lock external Docker CLI users or every ordinary lifecycle action.

Runs are process-owned. After backend termination, an abandoned run is marked interrupted when read. It is never silently resumed or replayed. Inspect Docker resources, completed step results and recovery metadata before taking manual action. This implementation requires a single controller with a local data volume; it is not a distributed job queue or a high-availability scheduler.

Standalone container duplicate and replace¶

Open an unmanaged standalone container's dedicated detail page. Choose Duplicate or Edit / replace, adjust the fields, then preview and confirm. The preview freezes the submitted request; source fingerprints and preview digests reject stale edits. The image must already exist locally.

  • Duplicate starts with a new name, stopped state, no published host ports and fresh anonymous local volumes. Source bind mounts are omitted. Copied static IPs and network aliases are removed. Explicit controls allow source mount sharing and port publication, with warnings about writers and port conflicts.
  • Replace checks dependencies, stops the source if running, disables its automatic restart policy, renames it to declarack-backup-..., releases network endpoints, creates the new container, reconnects additional networks, optionally starts it and verifies state/health. Actual named and anonymous volume identities, bind settings, declared network aliases/static IPs, limits and restart settings are preserved in normalized create configuration. Editing advanced JSON can intentionally change them.
  • Failure retains a stopped new container as declarack-failed-..., then disables its restart policy and attempts to restore the original name, network attachments, restart policy and running state. If replacement shutdown and restart isolation cannot be confirmed, the original stays stopped for manual recovery. Any recovery failure remains visible. Preflight failures do not mutate the source.

No container or volume is automatically deleted. Retained backups and failed containers consume storage and may still reference volumes; remove them manually only after verifying the result. A replacement creates a fresh image-based writable layer: files changed outside mounts are not copied. Recovery restores configuration, not application data modified on shared storage. This is not a filesystem snapshot.

Swarm tasks must be managed through services/stacks. Compose replacement must use the Compose project (duplicates drop Compose ownership labels). Replacement of the active controller, auto-remove sources, shared container namespaces, dependent namespace consumers and legacy links is refused. SELinux-relabeled bind mounts and unsupported mount kinds require deployment-managed recreation. Dependency scanning is bounded to 256 containers. There is no automatic image pull, cancellation, automatic retry, or crash recovery. Existing rename/network-connect/start actions and the retained run metadata support explicit manual recovery after inspection.

Implementation examples: backend/adapters/docker/recreate-operations.yaml, backend/adapters/docker/features.yaml, backend/adapters/docker/recreate.py, and backend/operation_runs.py.
