Users, sessions and TLS¶

Declarack uses local, database-backed administrator accounts and a dedicated login page. The protected Administrator role has full access to the installation, credentials and workloads. Configured roles restrict operations to targets; environments and navigation groups are not security boundaries. There are no teams, resource-label policies, signup, SSO or API keys. See role permissions. Login accounts are separate from target, Git and registry credential profiles.

First administrator¶

The optional system configuration block is:

auth:
  provider: local
  bootstrap_credential: installation_bootstrap
  session_hours: 8
credentials:
  installation_bootstrap:
    type: basic
    username: admin
    password: {file: /run/secrets/declarack_admin_password}

local is the only provider and the default. bootstrap_credential is optional and must reference a basic profile. session_hours is an integer from 1 to 168, defaulting to 8. The profile's username/password seed the first administrator only when the users table is empty. This does not enable HTTP Basic Auth.

Without that reference, first startup uses DECLARACK_ADMIN_USERNAME (default admin) and either DECLARACK_PASSWORD_FILE or DECLARACK_PASSWORD. Choose one password source; a mounted file is preferable. The file contains a single value; a trailing newline is accepted. These variables are bootstrap inputs, not live account settings. Startup without any initial password fails when no users exist.

Once accounts exist, changing bootstrap environment values or profile secrets does not change their passwords. The bootstrap password mount may be absent on later starts: it is not reread for existing users. Keep a referenced profile's configuration valid. Manage existing passwords through Administrators or host recovery instead of rotating bootstrap inputs. Accounts are database rows, not YAML documents. A profile with inline {value: ...} still leaves that bootstrap secret in configuration revisions, history and exports; prefer file references.

Manage users¶

Open Settings → Users (#/settings/~users) for the account list. Click a username or Manage to open that user's dedicated detail page. The You badge identifies your own account. The top-level Refresh reloads the list, account summary and activity; there are no separate card refresh buttons.

Choose Create user to open #/settings/~users/~new. Enter a username and password, then submit. Success opens the new account's detail page; Cancel returns to the list without saving. Usernames are immutable, 1–64 ASCII characters: the first must be a letter or number; subsequent characters may also be _, ., @ or -. Names are canonicalized to lowercase and unique. New and reset passwords must contain 12–1024 characters. The login form does not apply the new-password minimum to password entry. Choose one or more active roles when creating an account. The protected Administrator role grants full access; other roles use configured grants.

Details use #/settings/~users/USER_ID and separate Account summary, Password, Access, Sessions and Activity. Password fields appear only after Reset password. Disabling, enabling, resetting a password or signing out sessions requires a confirmation. Disabling an account or resetting its password revokes its sessions; Sign out all sessions also signs out all its sessions. Resetting your own password or signing out your own sessions signs you out immediately. You cannot disable yourself, and the backend protects the last enabled administrator. There is no account deletion. Role assignments have their own confirmation and revoke existing sessions. Navigating away clears password fields.

Global activity is collapsed on the list. User details filter the latest 100 installation events to the selected account; this is not an exhaustive per-user history. Account events are retained up to the existing 1,000-event bound and exclude passwords/session tokens. Accounts remain database rows, separate from YAML configuration.

Role permissions documents implemented enforcement and limits. The design roadmap describes later extensions.

Demo mode returns an authenticated demo session and bypasses login. Administrator management is explicitly unavailable in both backend and static demo modes.

Recover access from the host¶

Run this from an environment with the same database selection and access as the controller, with a file containing the new 12–1024 character password:

python -m backend.auth reset-password USER --password-file FILE

Replace USER with an existing username and FILE with its container/host-visible password file. This host-only command resets the password, reenables the account and revokes all its sessions. It does not create a missing user and has no HTTP recovery endpoint. Keep database access and recovery files restricted to operators. Changing DECLARACK_PASSWORD will not recover an existing account.

Sessions and API clients¶

Passwords use scrypt:32768:8:3 hashes. Login creates an opaque random session cookie; the database stores its SHA-256 hash, not the bearer token. Sessions have a fixed expiry (8 hours by default), with at most 20 concurrent sessions per user. The header shows the signed-in username and Sign out control. Signing out, reaching the session expiry timer, or receiving an API 401 unmounts protected UI and returns to login, preventing stale sensitive views from remaining visible. Login failures are throttled by username and client address: 10 failures block further attempts until the five-minute bucket expires.

The declarack_session cookie is HttpOnly, SameSite=Lax, and scoped to /. It is Secure when Declarack observes HTTPS, either natively or through an explicitly trusted proxy. Plain HTTP remains allowed for local development; it does not set Secure. Use HTTPS for remote access.

Endpoint Behavior
GET /api/v1/auth/session Public session discovery; anonymous response is {"authenticated":false,"demo":false}
POST /api/v1/auth/login JSON username and password; sets cookie and returns authenticated snapshot
POST /api/v1/auth/logout JSON {}; revokes current session and clears cookie
GET /api/v1/users Administrator list and current_user_id
GET /api/v1/users/activity Read-only account activity: {"events":[...]}, newest 100 retained events first
POST /api/v1/users Create with username and password
PATCH /api/v1/users/ID Change password or boolean disabled
POST /api/v1/users/ID/revoke-sessions JSON {}; revoke all sessions for the account

Authenticated snapshots include authenticated, demo, user, csrf_token and numeric Unix expires_at. Anonymous protected API reads return JSON HTTP 401, not a Basic Auth challenge. Writes must send X-Declarack-Action: 1; authenticated writes, including logout, must also send X-Declarack-CSRF with the snapshot's csrf_token and the session cookie. Login needs the action header but has no existing-session CSRF token. Cross-site writes are rejected; a supplied Origin must match the request origin. Non-browser clients may omit Origin but must supply the required action/CSRF headers. Keep the cookie jar and token private. A 401 requires a fresh login; refreshing session discovery supplies the current snapshot and token.

Account writes revalidate the caller's actual session hash, expiry and enabled account under the database account lock, after any password hashing. A session revoked while an account creation or password reset is queued cannot finish that write using its earlier request authentication.

Revocation prevents subsequent API access; it does not cancel work already accepted by an adapter or roll back a running operation. Existing terminal idle cleanup still bounds abandoned PTYs.

Account activity and audit scope¶

Settings → Administrators → Recent account activity is read-only. Account events are stored as generic documents in framework.auth.audit; the newest 1,000 are retained, and GET /api/v1/users/activity returns the newest 100 in {"events":[...]}. The endpoint requires an authenticated administrator and is unavailable in demo mode, like the rest of account management.

Recorded actions are user.created, user.password_reset, user.disabled, user.enabled, sessions.revoked and user.recovered. Events include the action, target user_id, Unix timestamp at, and actor identity (id, username and role for an administrator, or a type marker of bootstrap / host-operator). They contain no passwords, session tokens or other secrets. Account mutation and its audit event share the database transaction; older events are pruned rather than retained as an unlimited history.

Recorded operation plans separately include the actor in metadata.actor (id, username, role, or a system marker for non-user work). Batch fan-out propagates ContextVars into worker threads so those recorded plans preserve the initiating actor. Bounded account activity and plan metadata do not form a complete generic resource audit log or audit governance system; simple direct resource calls do not all produce recorded plans.

Native TLS¶

The process serves one HTTP or HTTPS listener through Cheroot. TLS is deployment configuration, independent of system YAML:

Variable Default / purpose
DECLARACK_TLS off; accepts off, files, self-signed
DECLARACK_TLS_CERT_FILE Certificate PEM path; required in files mode
DECLARACK_TLS_KEY_FILE Unencrypted private-key PEM path; required in files mode
DECLARACK_TLS_HOSTS localhost,127.0.0.1; comma-separated DNS/IP SANs for self-signed
HOST 127.0.0.1 in Python; Docker image sets 0.0.0.0
PORT 8080 with TLS off, 8443 with TLS enabled; explicit value overrides
DECLARACK_TRUSTED_PROXIES Empty: trust no forwarded headers; explicit comma-separated IP/CIDR list

The following commands assume an existing administrator database or the first-account bootstrap inputs, and valid target configuration/mounts. For a certificate issued by your CA, set:

export DECLARACK_TLS=files
export DECLARACK_TLS_CERT_FILE=/run/secrets/declarack_cert.pem
export DECLARACK_TLS_KEY_FILE=/run/secrets/declarack_key.pem
python -m backend.server

Mount those paths before startup. TLS requires a valid, currently usable matching certificate/key pair and TLS 1.2 or later. Encrypted private keys are unsupported. Certificate/key variables are accepted only in files mode. If you use containers, update the published port to the selected listener; an existing 8080:8080 mapping does not expose the default TLS listener on 8443.

For a locally trusted development/lab certificate:

export DECLARACK_TLS=self-signed
export DECLARACK_TLS_HOSTS=localhost,127.0.0.1
python -m backend.server

First startup generates a 365-day certificate and an unencrypted key at <DECLARACK_DATA>/tls/cert.pem and key.pem (normally /data/tls). Generated files start with mode 0600; the private key is enforced as 0600 on reuse. The pair is persisted and reused, not regenerated on every restart. Trust the certificate explicitly on clients. Persist it even when the database is external PostgreSQL.

Certificates load at startup. Replace files and restart to reload; there is no ACME integration, automatic renewal, hot reload, or HTTP-to-HTTPS redirect listener. An expired pair fails startup. A changed DECLARACK_TLS_HOSTS must be covered by the existing SANs; to generate a replacement, stop the controller, back up and remove both generated files, then restart with the new hosts. Reestablish client trust. An incomplete persisted pair fails startup rather than replacing one half.

HTTPS reverse proxies¶

You may terminate TLS at a reverse proxy and keep DECLARACK_TLS=off internally. Set DECLARACK_TRUSTED_PROXIES to the immediate proxy's actual IP or CIDR. Only requests from those peers honor one rightmost X-Forwarded-Proto and X-Forwarded-For hop. The proxy must overwrite or append its observed scheme and client address. Forwarded host, port and URL prefix are never honored; preserve the public Host header and deploy at the origin root. Arbitrary forwarded headers from untrusted peers cannot mark an HTTP request secure.

Without proxy trust, HTTPS termination appears as HTTP to Declarack, affecting Secure cookies and Origin verification. Keep the internal listener reachable only by intended peers and configure the proxy and explicit trust list together.

Upgrade from Basic Auth¶

This is a breaking configuration and client change. Replace auth.provider: basic with local and rename auth.credential to auth.bootstrap_credential. Older auth.username / auth.password_file fields must also move into a referenced basic bootstrap profile or the bootstrap environment variables. Import the updated configuration under the normal configuration authority rules. A restart alone retains the active database revision. To apply changed authentication bootstrap/settings from files, publish/export the intended documents and restart once with DECLARACK_CONFIG_FORCE_LOAD=1, then remove that flag.

No HTTP Basic Auth requests are supported. Browser Basic Auth and scripts using curl -u must migrate to login, cookies and CSRF/action headers. On an installation with an empty users table, the bootstrap seeds the first account; thereafter manage it in the database. See credentials for outbound HTTP Basic, Git and registry profiles, which remain separate supported uses of basic.
