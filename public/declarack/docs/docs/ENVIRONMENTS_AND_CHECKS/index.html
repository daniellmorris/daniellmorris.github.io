Targets, environments, and persisted checks¶

A target is a connection with its enabled interactive features. An environment groups targets and optionally links to custom pages. A target can belong to several environments or none. Environment membership does not grant or restrict execution permissions.

Without an environments section, each target is presented as its own environment alongside the reserved root (Home) environment. An explicit environments: {} leaves only root. Root never implicitly includes targets. The installation-wide Targets page lists all connections. Root navigation controls links to Targets, Settings, Checks, Operations and the environment directory. Other environments place their own pages and fleet tools.

targets:
  host:
    connection: docker_socket
    socket: /var/run/docker.sock
    features: [containers, images, volumes]
  public_api:
    connection: http
    base_url: https://status.example.com
    features: []

environments:
  local:
    label: Local infrastructure
    targets: [host]
    # pages: [operations]  # Optional IDs of existing custom pages.

operations:
  website.health:
    check_safe: true
    bindings:
      http:
        executor: http.request
        path: /health

checks:
  docker:
    title: Docker connection
    target: host
    every: 60s
    failure_threshold: 3
    recovery_threshold: 2
  public-api:
    title: Public API readiness
    target: public_api
    operation: website.health
    healthy: 'status = "ok"'
    every: 30s
    failure_threshold: 2
    recovery_threshold: 1
    enabled: true

The public API target is ungrouped and enables no visible features, but checks can still use it. Environment groups keep their targets' features; they cannot define or override features themselves. Grouped pages reference existing custom pages.

Where checks are stored¶

Definitions live in system YAML, including configuration folders. You can create/edit check fragments in Settings, save them, then reload configuration. They are backed up and deployed using the same workflow as the rest of the config. There is no separate database copy of check definitions or check builder UI.

Runtime monitoring state lives in the shared database: /data/state.sqlite by default, or configured PostgreSQL. It stores current state, consecutive result counters, last collection/success, next due time, operator pauses and recent results. Persist the database to retain this information; YAML definitions remain separate. See storage setup and legacy import.

The scheduler runs in the backend, even when no browser is open. Each check is scheduled again from completion time. A missed interval during downtime is not replayed; an overdue check runs after restart. Runs are serialized in this first version, so long upstream operations can delay other checks. Adapter transport and command timeouts still apply; there is no per-check timeout override or cron syntax. JSONata evaluation has a 1-second evaluation guard, stack depth 100, and sequence limit 10,000; these are interpreter guards, not process isolation.

Only one scheduler acquires the filesystem lock in a shared data directory. Deploy one Declarack replica for monitoring in this version. Separate data volumes create independent schedulers; SQLite and a file lock are not a distributed coordination service. Use a local persistent filesystem with working file locks.

Check behavior and limits¶

  • Omit operation for an adapter connection probe. This tests connectivity, not overall workload health. The HTTP probe tolerates many non-server-error HTTP responses; use an explicit health operation when response content matters.
  • An operation check executes a compatible inventory/detail read, or a custom operation explicitly marked check_safe: true. This is an administrator's assertion about custom operation behavior, not a sandbox. Do not mark modifying commands safe. Non-GET/HEAD HTTP/Docker bindings cannot be scheduled.
  • Checks do not need the operation's feature enabled on the target. This does not enable that operation in the general target operation API.
  • inputs uses the operation's existing input schema. healthy is JSONata evaluated directly against the operation result. It must return a boolean. Omission means a successful operation is healthy. Errors, missing/non-boolean results, and evaluation failures count as failed results.
  • every accepts integer seconds or an integer duration ending in s, m, or h; minimum 10 seconds, maximum 24 hours. It defaults to 60 seconds.
  • Failure/recovery thresholds are consecutive results, each 1–100 (default 1). Counters reset on the opposite result. The initial state is unknown; it changes only after the corresponding threshold is reached. A prior healthy state can remain healthy while failures are still below threshold; the latest result and failure counter remain visible.
  • enabled: false disables the check through configuration. Operator Pause/Resume is persisted separately. Paused/disabled checks cannot be run manually. A run already in flight may finish when Pause is pressed.
  • Check or target definition changes reset the current evaluation state and due time. Runtime pause remains. Previous history remains visible. Removed checks are no longer scheduled; stale in-flight results from changed/removed checks are discarded.
  • At most 256 checks; at most 100 results per check and 25,600 results globally. Operation response bodies are not stored in monitoring history.

Alarms and the UI¶

Checks shows current alarm state, latest result, last success, schedule, and consecutive result counts. Select a check for its dedicated history page. Run now, Pause, and Resume use authenticated action endpoints. The page refreshes state every 10 seconds without triggering extra check executions.

A transition into failing is a local alarm; a transition into healthy records recovery. This release persists/displays transitions but does not send webhook, email, or other outbound notifications. Maintenance windows, alert acknowledgments, notification adapters/delivery retries, uptime percentages, and a public status page are future extensions.

API endpoints:

  • GET /api/v1/checks: configured checks and persisted status.
  • GET /api/v1/checks/<id>: status plus up to 100 recent results.
  • POST /api/v1/checks/<id>/run: run now and persist its result.
  • POST /api/v1/checks/<id>/pause and /resume: persist an operator pause.

Writes require the usual authentication and X-Declarack-Action: 1 header. The real lab includes grouped environments and manager/Grafana connection checks. Copy examples/multi-environment/optional/checks.yaml into its runtime config folder for a JSONata Grafana database check using an additional ungrouped target.

Custom pages can be global, environment-only, or both: see page placement. Environment pages and batches lists place tools in selected groups; root controls Home and installation-wide navigation.
