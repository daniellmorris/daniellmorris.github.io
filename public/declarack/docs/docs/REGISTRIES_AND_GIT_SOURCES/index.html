Registry credentials and Git stack sources¶

Define reusable credentials through Settings → Credentials, then reference IDs in targets. Both entered values and mounted-file paths use the same profiles; see credential management. Target registry settings map hosts to basic profile IDs, and git_credentials lists allowed basic/SSH profile IDs. Save and activate configuration before use. Registry and Git authentication remain separate execution scopes even when profiles are reused.

Configure target credentials¶

targets:
  production:
    label: Production Swarm
    connection: docker_socket
    socket: /var/run/docker.sock
    swarm: true
    features:
    - overview
    - services
    - nodes
    - tasks
    - stacks
    - configs
    - secrets
    - networks
    - volumes
    registry_credentials:
      ghcr.io: registry_ghcr.io
      registry.example.com:5000: registry_registry.example.com_5000
    git_credentials:
    - company_https
    - company_ssh
credentials:
  registry_ghcr.io:
    type: basic
    username: example-user
    password:
      file: /run/secrets/ghcr_token
  registry_registry.example.com_5000:
    type: basic
    username: deploy
    password:
      file: /run/secrets/registry_password
  company_https:
    type: basic
    username: deploy
    host: git.example.com
    password:
      file: /run/secrets/git_token
  company_ssh:
    type: ssh
    username: git
    host: git.example.com
    private_key:
      file: /run/secrets/git_key
    known_hosts:
      file: /etc/declarack/git_known_hosts

Replace target IDs, addresses and usernames, and mount the referenced files before using the credentials. Include a port in the Git credential host when the URL uses one. HTTPS tokens and SSH keys are different profile types; SSH URLs must include the remote user, for example ssh://git@git.example.com/team/app.git. SSH requires an explicit identity and known-hosts profile. HTTPS repositories without authentication can leave the credential field empty.

Profiles are scoped to one target. A Git credential can only authenticate to its configured host and transport; redirects are refused. Registry credentials apply by image hostname. For Docker Hub use docker.io; it is normalized to Docker's https://index.docker.io/v1/ authentication key. Include a port for a non-default registry port. Do not put paths or embedded credentials in registry hostnames. Registry TLS/trust and any insecure-registry policy remain Docker engine/client configuration; this feature does not disable certificate verification.

Registry execution¶

Configured credentials are available to standalone image pulls, existing standalone Compose deployment workflows, Swarm stack deployments, and reviewed Swarm service edits. Compose and stack commands receive a target-scoped temporary Docker config.json, removed after the command finishes. Swarm stack deployment adds --with-registry-auth so workers can pull private images. Service edits send a matching X-Registry-Auth header. Rollback retains Docker's previous-spec auth.

Credential files are read when an operation runs, so replacing a mounted token file does not require saving every stack again. Existing running services do not receive rotated credentials until an update/deploy forwards them. All configured registry files for a target must be readable for a Compose up or stack deploy. Read-only previews and stop/remove operations do not load registry credentials. When no registry profiles are configured, CLI workflows use the existing /etc/declarack/docker config-directory convention.

Registry authentication is separate from source-repository access: a Git PAT does not authenticate an image pull. There is no registry catalog browser, image-push workflow or credential-value editor in this change.

Use a general Git source for a Swarm stack¶

  1. Open Stacks → New stack, or edit a saved source.
  2. Select Git repository (HTTPS / SSH).
  3. Enter the repository URL, ref and relative Compose path.
  4. Select a configured Git credential, or leave it empty for public HTTPS.
  5. Save source, preview, validate, then deploy through the existing confirmation.

Refs can be HEAD, a branch such as main or release/next, a tag, full refs/heads/main / refs/tags/v1.2.0, or a full commit ID. Use full refs when a branch and tag share a name. The server must permit fetching the selected ref or commit; this is not a full-history clone. The default Compose path is compose.yaml; set docker-compose.yml or a nested path explicitly when needed.

Source retrieval uses Git's HTTPS/SSH protocols, rather than a provider-specific archive API. This supports GitHub, GitLab, Gitea/Forgejo and other compatible Git servers. Submodules, Git LFS materialization and symlinks are not supported. Retrieval uses isolated Git configuration, bounded commands and a bounded regular- file archive. Relative Compose config/secret files resolve from the selected Compose file's directory. Bind-mounted host paths still need to exist on the Docker nodes; downloading a repository does not provision files onto workers.

Preview reports the resolved commit and Compose digest. Deploy retrieves the source again and refuses to proceed if the ref moved or the reviewed content changed. Preview again to deploy a new revision. This is explicit deployment, not an automatic GitOps reconciler or webhook integration.

Persistence and redeploy¶

The saved Swarm source record stores git_url, ref, git_path and the credential profile ID in target-scoped documents in the shared database. It stores the last deployed commit too. General Git source records store only the profile ID. The profile stores either a mounted-file reference or an entered value in system configuration. Redeploy reads the saved metadata, resolves that target's allowed named profile and reads its current credential source. Persist the configured database to retain saved source records; keep configuration and secret mounts available after container replacement.

The older GitHub tag creation mode and per-stack PAT editor have been removed. Legacy stored records may remain as historical data. Its username/PAT storage still uses an encrypted per-stack token and target encryption key, both retained in the configured database (and copied by legacy import). New Git sources use named inline/file-backed profiles instead.

General Git sources are currently offered for Swarm stacks. Standalone Compose retains inline and mounted-folder source modes; it gains registry credentials but not the new Git source editor in this change.
