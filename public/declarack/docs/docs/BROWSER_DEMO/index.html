Static browser playground¶

The browser playground runs Declarack’s existing React renderer against a simulated API in a service worker. It needs static hosting only: no Python, Docker socket, remote hosts or hosted database. Every visitor gets their own browser-local configuration and inventories; tabs on the same origin share them.

Run locally¶

npm ci --prefix frontend
npm run demo --prefix frontend

Open http://localhost:9083. This builds the demo and starts a static preview server. The existing Python DECLARACK_MODE=demo remains a separate option.

The banner labels the infrastructure as simulated and offers Reset demo. Changes survive reloads in the browser’s Cache Storage, including saved and active configuration revisions and up to 20 document snapshots. Reset restores the supplied configuration and inventories. Clearing site data also removes them. There is no shared server-side state or account system. Use example credentials only; entered values are browser-local data, not a secure credential vault.

Try the workflows¶

  1. Open Production → Swarm A → Services. Scale a service, then reload its overview. Swarm B has an independent inventory.
  2. Open standalone Docker to start/stop/pause containers, inspect health-check JSON, remove resources, pull a simulated image, or collect volume sizes.
  3. Open Fleet dashboard to query both Swarms and standalone Docker together. Monitoring includes simulated Grafana dashboards and Prometheus scrape targets; the SSH host supports sample metrics and simulated command output.
  4. Open Settings, select dashboard.yaml, change a page title or columns, then Review & save file → Save configuration → Activate configuration. Saving and activation remain separate, just as in the real application.
  5. Try the Credentials editor using synthetic values, or copy example snippets.
  6. Reset the playground when finished.

This is a curated simulation, not a Docker emulator. Unsupported actions return an explicit demo error. Terminals, real connection tests, stack deployments, arbitrary command/HTTP execution, scheduled check execution and source-provider import/publication require the real backend. Configuration validation checks the demo’s supported structure; it does not execute Python adapter validators. New custom pages/features can reuse simulated operations, but new operation definitions do not automatically gain an executable simulation. Configuration containing scheduled checks does not start a scheduler in the browser.

Publish on static hosting¶

npm ci --prefix frontend
npm run build:demo --prefix frontend

The same demo can be built at a domain root or under a subpath. For a subpath, include its leading and trailing slashes:

npm run build:demo --prefix frontend -- --base=/declarack/demo/

Publish frontend/dist-demo/ at that exact directory on an HTTPS static host. Asset URLs, API requests, the worker registration/scope and Reset demo all use the build base. The worker handles only API paths inside its own directory; sibling documentation and the rest of the website are outside its scope. State is stored under a key derived from that scope, so different demo paths remain independent. HTTPS is required except on localhost. If a normal app replaces a demo at the same path, its bootstrap unregisters that path’s known worker and reloads before making API calls.

Our public locations are:

  • Browser demo
  • Documentation
  • Project links

The Documentation and demo workflow builds both outputs, validates links and demo contracts, then publishes generated files to public/declarack/ in daniellmorris/daniellmorris.github.io. Its existing Astro Pages workflow deploys them with the personal website. Application source remains in the private repo; only the curated docs and compiled demo are copied. The website’s other source files and pages are preserved. Pull requests build an artifact without publishing.

Publishing uses the DECLARACK_SITE_DEPLOY_KEY Actions secret: an SSH deploy key restricted to the website repository. Its GitHub permission allows repository writes; the publisher script limits its own changes to generated Declarack paths. Rotate it by replacing the website deploy key and the private repository secret. Do not add real credentials or private environment snapshots to demo fixtures or published documentation. The output is public by design.

For local verification of the complete site bundle:

npm run build:demo --prefix frontend -- --base=/declarack/demo/
DOCS_SITE_URL=https://daniellmorris.com/declarack/docs/ .venv-docs/bin/python tools/docs.py build
.venv/bin/python tools/site.py

The assembled .site-build/ contains demo/, docs/ and a link page. The regular Build workflow still offers a standalone declarack-browser-demo artifact for root hosting; no Python server, Functions or database binding is required.

Maintain the simulation¶

  • frontend/src/demo/config.yaml: editable default configuration; uses production schemas, features, operations and JSONata mappings.
  • frontend/src/demo/seed.json: generated, checked-in adapter contracts and synthetic Docker fixtures. No real environment snapshots or credentials.
  • state.mjs, api.mjs, operations.mjs: demo-only state, API contracts and explicit simulated operations.
  • worker.js: intercepts same-origin /api/ requests, serializes updates and persists state. Unknown API requests fail locally; there is no network fallback. Static asset requests continue to the static host.
  • bootstrap.js: registers the worker before the renderer mounts and adds the demo banner/reset control.

After changing built-in feature/operation YAML, fixtures or default demo config:

.venv/bin/python -m tools.demo_seed
npm run test:demo --prefix frontend
npm run build:demo --prefix frontend

The exporter validates the default configuration using the actual Python Dashboard and adapter discovery without opening network connections. CI runs python -m tools.demo_seed --check to detect stale generated contracts. The JSON is checked in so static hosts need only Node to build the playground.

A normal npm run build --prefix frontend excludes the demo modules, worker and YAML parser from its emitted JavaScript. The Docker image continues to serve that normal production build. Simulation code stays outside the framework and adapters.
