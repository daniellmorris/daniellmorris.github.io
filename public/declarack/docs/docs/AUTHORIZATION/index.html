Roles and operation permissions¶

Declarack authorizes named operations per target. Role definitions are part of system configuration; user accounts store their assigned role IDs in the database. The backend enforces grants before execution and filters presentation metadata. The protected built-in administrator role retains full installation access.

Configure, activate, assign¶

  1. Add roles to configuration through Settings or import files. Review and save.
  2. Activate configuration. Saving a draft does not change permissions.
  3. Open Settings → Users, choose an account and select its roles. Review Effective permission grants, then Save roles and confirm. Assignment changes revoke that account's existing sessions; it signs in again with its new access.
  4. Test with a separate restricted account before reducing another administrator's access. The last enabled Administrator cannot be removed or disabled.

For a complete standalone example, use configurations/roles.yaml. In an existing config, replace engine below with an actual target ID and enable the referenced features:

roles:
  observer:
    label: Observer
    grants:
      - targets: [engine]
        operations: [containers.list, images.list]
  operator:
    label: Container operator
    grants:
      - targets: [engine]
        operations: [containers.list, containers.stop, containers.start]
  user_directory_reader:
    label: User directory reader
    grants:
      - operations: [system.users.read]

Grants contain explicit operations and optional targets lists. Target operations require target IDs and must be enabled on every listed target. Installation grants omit targets. Unknown operations/targets, wildcard IDs, unsupported fields and redefinitions of administrator/admin are rejected. Empty role grants are valid and confer no access; an account must have at least one assigned role ID. Multiple roles combine their grants. There are no deny rules or environment-based implicit grants. Environments remain presentation groups and may overlap.

Role IDs use lowercase letters, numbers, underscores and hyphens, starting with a letter, up to 64 characters. Labels are display text up to 120 characters. A role can contain up to 100 grants, each with up to 500 explicit operation IDs.

What the first version supports¶

  • Target-scoped foreground operations, including configured HTTP/SSH operations, node-local Swarm reads and explicit interactive terminal access.
  • system.users.read: read user records and account activity.
  • system.users.manage: create/manage accounts within the caller's own authority; implies user-directory read. Delegated managers cannot assign Administrator or manage another account whose grants exceed their own.
  • Protected Administrator: configuration, credential administration, roles editing, legacy Docker APIs, batches, bulk execution, checks/schedules and run history. Those installation APIs remain Administrator-only in this release.

Background mutation plans also remain Administrator-only. A generic binding field execution: background marks these operations in the catalog; the run store rejects non-admin admission independently of metadata. Scoped service principals and non-admin background delegation are deferred, not silently elevated.

Granting containers.list shows inventory but does not grant details, logs, inspection, removal or shells. A feature appears when its inventory and required selector operation are allowed. A detail link needs its inspect operation. Forms need permitted actions and lookups; unavailable workflows are omitted. On a Swarm, a node-selector view also needs swarm.nodes.list. Hidden transport actions for an authorized terminal open are included automatically; do not grant transport IDs alone. Core backend checks remain authoritative for direct/crafted requests.

Mixed-permission custom dashboards are hidden as a whole if any source is denied. This avoids leaking hidden target names or producing misleading partial totals. Per-source dashboard redaction is deferred. Related-resource sections with denied operations are omitted. No-access accounts receive an empty state with Sign out.

Inspection, shells and credentials¶

Read-only operations can still expose sensitive data. Raw inspect/file reads can include environment variables, mounted data and credentials. Grant shell access or arbitrary SSH commands explicitly. The example Observer intentionally omits them. Configuration/credential administration remains trusted Administrator work because changing a command, target connection or role can expand authority.

An operation's documented output is its permission contract. For example, swarm.tasks.list may resolve service/node names internally; this does not permit arbitrary service/node API execution. Node-local read helpers can create temporary Swarm jobs internally without granting users a general service-creation capability.

Revocation, sessions and storage¶

Role grants come from active configuration on each request. Assignment changes revoke login sessions. Active role-definition changes invalidate the capability revision; the frontend checks session metadata every 30 seconds and also refreshes metadata after forbidden requests. Stale buttons do not bypass server checks. A request already executing may have issued external effects; revocation does not promise rollback of those effects.

Terminal transport checks ownership, target and current permission to open that session. Leases contain hashed tokens, user/target/open-operation references and an expiry. They are bounded to 1,000 recent records and one hour; actual terminal idle/runtime limits remain shorter. Denied or revoked transports cannot send or receive data. Existing processes are subject to terminal cleanup/idle limits; revocation is not a guarantee of immediate process termination.

Assignments use the shared framework.auth.roles document namespace, with a one-time migration marker. Existing accounts migrate to protected Administrator. A missing assignment after migration fails closed rather than becoming admin. Terminal ownership uses framework.auth.leases. Both live in the existing database and are included in its backup/transfer path; no separate policy files or database schema migration are required. Account role changes are recorded in account activity.

Account writes and policy activation share a cross-process advisory lock (SQLite file lock or PostgreSQL advisory lock), in addition to account transaction locks. Concurrent changes return HTTP 409 for retry.

Removing a role referenced by an account is rejected at activation. Reassign users first. External force-load can leave unknown assignments: those grants fail closed, while built-in Administrator and host recovery remain available. Host recovery restores the protected Administrator role as well as password/access.

A controller authorizes against its loaded active configuration. With multiple controllers, an instance that detects a different active database revision fails closed with HTTP 503 until restarted. Automatic multi-controller configuration synchronization and scoped background identities are not implemented.

API and discovery¶

  • GET /api/v1/roles returns assignable role definitions, management capability and a target/operation catalog limited to the caller's authority.
  • User creation accepts roles: [role_id, ...]. User updates accept roles alongside existing password/disabled changes. Empty or unknown assignments are rejected.
  • Session and target metadata return an authorization revision; target metadata contains filtered features, actions, pages, environments and settings sections.
  • Unclassified installation endpoints and legacy paths deny non-admin requests.

See users and TLS for account workflows and recovery, and the design and roadmap for deferred resource constraints.
