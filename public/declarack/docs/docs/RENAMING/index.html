Upgrading to Declarack¶

Declarack is the new name for the application and its configurable administration framework. Existing Docker/Swarm features remain part of Declarack. There is no separate framework package to install.

New names¶

Interface Current name
Product, login realm, HTTP user agent Declarack
Repository daniellmorris/declarack
Published image path for subsequent builds ghcr.io/daniellmorris/declarack
Runtime variable prefix DECLARACK_
Default config/adapter/CLI credential directory /etc/declarack
Compose service / logical data volume declarack / declarack-data
Current database state.sqlite by default, or PostgreSQL; legacy stack databases require import
Action request header X-Declarack-Action: 1
New job labels / names io.declarack.worker-job, declarack-*

The main YAML can still be named dashboard.yaml. Its keys (targets, features, operations, auth, legacy_workspace) and resource routes have not been renamed. DOCKER_SOCKET, HOST, and PORT remain unchanged.

Existing settings and data¶

Legacy SWARMDECK_* process variables are accepted as fallbacks. If both prefixes are present, the explicit DECLARACK_* value wins, including an empty value. New deployment templates use only the new names. Docker Compose's own substitution now expects the new names; backend fallbacks do not rewrite your Compose .env file.

Current releases use the shared storage service, defaulting to state.sqlite. Stop the controller and explicitly import an old data directory before using it. Legacy import reads swarmdeck.sqlite when declarack.sqlite does not exist, copies encrypted PATs and credential.key into database documents, and preserves the original files. If both old names exist, declarack.sqlite wins; investigate before combining data. Target IDs continue to determine source scopes.

Browser preferences are copied from old keys when a matching new key is absent. The legacy action header remains accepted during upgrades; new clients send the Declarack header. Existing worker labels remain recognized for resource filtering and expired-job/network cleanup. New jobs use Declarack labels.

Docker Compose upgrade¶

Renaming a Compose service does not rename an existing running container or volume. Before switching, inspect your existing deployment and identify its actual data volume name. Stop the old dashboard service to release port 8080, then deploy the new service with the same data volume explicitly attached. Do not remove that volume. For example, an additional override can reuse a volume already present:

volumes:
  declarack-data:
    external: true
    name: YOUR_EXISTING_DATA_VOLUME_NAME

Use the exact name from docker volume ls/the existing container's mount inspection. The logical volume name in the new Compose file is declarack-data; Docker's actual volume name may be project-prefixed. Without a reuse mapping, a renamed deployment can create a fresh empty volume. Keep the previous volume and a backup until verified.

Update environment names, service references in overrides, image names, mounted /etc/declarack paths, and any DECLARACK_CONFIG_SERVICE references. Paths explicitly stored in your YAML can remain old paths if you keep mounting files at those paths; the application does not automatically rewrite target configuration files.

Rebuild/publish the renamed image and update Swarm agent_image references to the same build, preferably by digest. Renaming a GitHub repository does not move old GHCR packages. Previous image names/digests are not deleted or republished as part of the source rename. Update deployment automation and image-pull credentials as needed.

The active local checkout directory is not moved while Codex is using it. Its Git remote can point to the renamed repository independently of the checkout folder name.
