Configuration folders and reload¶

System configuration is now database-managed. A folder is imported once into logical database documents; its merge rules remain unchanged. To reimport after external edits use Settings → Review import from files, or set DECLARACK_CONFIG_FORCE_LOAD=1 for startup imports. GUI edits save database revisions and Activate configuration applies them. Enable DECLARACK_CONFIG_WRITE_BACK=1 to write files before activation. Source mounts may be read-only for DB-only editing. See authority, flags and recovery. The filesystem mechanics below describe source import/write-back and the original file provider, rather than a requirement to maintain live YAML files for DB mode.

DECLARACK_CONFIG accepts either one YAML file or a directory. A directory is simply one large configuration merge. Its files are not independent packages and their directory names have no special meaning. After merging, Declarack validates the same targets, operations, features, pages, and authentication model used by a single-file installation.

Start with the example¶

The image includes /app/configurations/folder-example; the repository copy is configurations/folder-example. It contains:

folder-example/
  00-system.yaml
  10-targets/host.yaml
  20-pages/engine.yaml
  90-overrides.yaml

Use it directly in an image by setting DECLARACK_CONFIG=/app/configurations/folder-example, or copy it into an editable host directory and mount that directory:

services:
  declarack:
    environment:
      DECLARACK_CONFIG: /etc/declarack/config
    volumes:
      - ./my-config:/etc/declarack/config:ro

This is a deployment override used with the repository's base compose.yaml. Keep its password, Docker socket, and data configuration. A read-only container mount is sufficient for external file edits and Reload configuration; GUI editing or creating files additionally requires a writable mount and DECLARACK_CONFIG_EDIT=1 (see below).

Exact merge rules¶

  1. Find .yaml and .yml files recursively beneath the configured directory.
  2. Ignore hidden files/directories such as .git, and non-YAML files such as editor temporary files and .previous backups.
  3. Sort by relative path, case-sensitively, then load in that order.
  4. Merge mappings recursively. A later scalar, list, or different type replaces the earlier value at that key.
  5. Validate the resulting single configuration before using it.

For example:

# 10-targets/host.yaml
targets:
  host:
    label: Original label
    connection: docker_socket
    socket: /var/run/docker.sock
    features: [containers, images]

# 90-overrides.yaml
targets:
  host:
    label: My Docker host
    features: [containers]

The result retains the connection and socket, replaces the label, and enables only containers. Lists do not concatenate. Overriding columns, actions, cards, or feature lists means supplying the complete desired list.

Each file is a normal root configuration fragment. A file under targets/ still needs its targets: wrapper; no section is inferred from its filename. You can keep related target/operation/feature/page definitions together in one file or split them among several. A commented-out/empty document contributes nothing.

There is no include syntax, environment interpolation, deletion marker, or special merge directive. null is a value, not a delete instruction. Duplicate YAML keys inside one file fail; repeated keys across files follow the merge rules above. YAML << merge keys are not supported by the system-config parser. Custom IDs still must not collide with built-in adapter IDs/definitions.

Limits are 256 YAML files and 1 MiB combined source contents. File symlinks must resolve within the configured folder; symlink directories are not traversed. A dedicated config directory avoids accidentally loading unrelated YAML files.

Reload workflow¶

  1. Edit, add, or remove source files.
  2. Open top-level Settings.
  3. Optionally select Read source files to inspect the updated file list and merged YAML. The file selector shows each original source without flattening it.
  4. Select Reload configuration to validate and apply the current disk snapshot.

The reload action reads a fresh snapshot and submits its revision. Revisions cover filenames, contents, additions, removals, and renames. A concurrent edit detected during validation causes a conflict instead of applying the stale candidate.

If parsing or validation fails, the running model stays active. Correct the source and retry. Parse errors identify the source filename; semantic validation errors identify affected configuration IDs/references. A read failure does not erase the currently running targets or pages.

Reload supports changes to targets, operation definitions, feature definitions, and custom pages using the adapters already loaded at startup. Removed or changed SSH targets retire their old forwards. New connections are still opened lazily; a successful reload validates configuration, not upstream availability.

Changes to authentication, credential values used for installation login, or the legacy workspace identity/connection require a restart. New/changed adapter Python, process environment variables, ports, and mounts also require deployment/restart. Reload does not load new application code. Other open browser clients may need a page refresh to obtain changed navigation/feature definitions.

There is no filesystem watcher/background auto-apply in this version. Reload is explicit and revision-checked. This makes a safe foundation for a future GUI edit/validate/preview/apply workflow without adding a second configuration store.

Single-file and storage compatibility¶

Existing single-file configurations keep working. Their file-store Settings editor retains its current save behavior and protected-definition policy. External edits to a local single file can also be applied with Reload configuration; unsaved browser drafts must first be saved or discarded.

Folder-backed Settings includes source browsing, merged preview, validation, connection testing, reload, and optional New file creation. Test all connections checks every target in the displayed configuration and reports each target’s pass or failure independently; testing does not save or apply the configuration. It never saves the merged document back over the source tree. Select an individual file in Configuration source to edit it when DECLARACK_CONFIG_EDIT=1 and the folder mount is writable. The merged view stays read-only.

For an existing source, use Validate file, then Save file, then Reload configuration. Saving validates the complete resulting merge, checks that the source revision has not changed, atomically replaces only that file, and retains its prior contents as <filename>.previous. It preserves file permissions and does not apply runtime changes until reload. Unsaved drafts must be saved or discarded before selecting another file or reloading. Symlink files and paths through symlink directories cannot be edited. File deletion is done on disk.

To enable creation, set DECLARACK_CONFIG_EDIT=1 and mount the configuration folder writable. In Settings, select New file, enter a relative .yaml or .yml path (nested folders are supported), and enter a root configuration fragment. Validate new file checks the entire resulting merge without writing anything. Create file validates again and atomically creates the file without overwriting an existing path. Then select Reload configuration to apply it.

Hidden paths, parent references, absolute paths, and symlink directories are rejected. The normal file-count and combined-size limits still apply. If the source revision changed, Read source files refreshes it while preserving the new-file draft. Creation requires the same authenticated action protection as other writes.

The API equivalents are POST /api/v1/settings/files/validate and POST /api/v1/settings/files, both with {path, yaml, revision}. Creation returns updated source metadata and created_path; it does not change the running model. Use PUT /api/v1/settings/files with {path, yaml, revision} to save an existing source. For a validation preview of an existing source, include existing: true when posting to /api/v1/settings/files/validate. Use POST /api/v1/settings/reload with the new revision to apply the merge.

Folders currently use local file storage. The GitHub and Swarm Settings stores continue to require a single file and retain their PR/redeployment behavior. A folder can still be delivered by your deployment pipeline from Git; that does not make it a GitHub Settings store. Packaging a folder into Swarm configs is a future capability, not an implicit behavior of this loader.

Try a new Grafana feature in the real lab¶

The multi-environment lab now generates its five-target configuration under runtime/config/ and loads that directory. After building/updating its Declarack container, copy the supplied optional fragment:

cp examples/multi-environment/optional/grafana-health.yaml \
   examples/multi-environment/runtime/config/50-grafana-health.yaml

Open Settings and select Reload configuration. You get a new Grafana health feature and a Grafana status custom page, backed by the real Grafana /api/health response. No frontend rebuild is needed to load that definition. This is a complete example of one fragment adding an operation, feature, target capability, and page.

Delete that extra file and reload to remove the additions. The example's overridden Grafana feature list explicitly retains its existing dashboard inventory feature. lab.py configure regenerates the five base fragments but preserves extra files such as this one; later overrides continue to take precedence.

Reload API¶

For authenticated clients:

GET  /api/v1/settings
POST /api/v1/settings/reload
     Content-Type: application/json
     X-Declarack-Action: 1
     {"revision": "revision-returned-by-the-read"}

Folder reads include ordered files (path, original yaml), merged yaml, revision, directory: true, writable: false, and reloadable: true. Reads expose administrative configuration and use the same authentication as Settings. Reload returns its accepted revision and message; errors leave the current model active.

Reviewed edits and recovery¶

Settings now offers Review & save file and Review new file. Review validates the proposed full merge, shows the source-file diff and effective merged-config diff, and allows inspecting the proposed merged YAML. Saving checks the revision again; concurrent source changes require a fresh review. Saving writes the file; Reload configuration applies it separately. Authentication and legacy-workspace changes can require a restart.

Revision history keeps up to 20 source snapshots per local configuration source in the shared database (/data/state.sqlite by default, or PostgreSQL). Persist that database to retain history across container replacement; see storage. History begins with the first save through the reviewed editor, including the pre-edit content. External edits and integration-wizard writes are not independently recorded. Source snapshots include all current YAML files, but restore operates on one selected file: Restore to draft, review, save, then reload. Restored content is validated against the other files as they exist now. This is not an atomic rollback of an entire folder, and it does not remove newly added files. Git and Swarm-config providers retain their own publication/history workflows. Drafts remain in the open page; they are not persisted automatically.
