Integration templates and dynamic form options¶

Declarack can generate an integration from an installed template and populate form choices from configured operations. These are reusable framework capabilities: adapter folders and trusted configuration supply the definitions; the frontend has no Docker/Grafana/SSH setup branches.

Add an integration¶

Open Targets → Add integration (also available from Settings).

  1. Choose a template and enter a unique target ID, display name and connection settings.
  2. Optionally choose an environment ID or type a new one. Blank leaves the target ungrouped. Existing environments retain their current targets and page assignments.
  3. Review the generated YAML. Declarack validates the complete merged configuration, including operation references, connection settings and source-file ordering.
  4. Optionally test the draft connection. This runs the connector's ordinary probe; it does not save the target or verify every resource permission/API endpoint.
  5. Save the integration as a new configuration fragment, then Reload configuration. Use Edit saved YAML to open that exact source file in Settings.

Saving requires a writable folder-backed configuration and DECLARACK_CONFIG_EDIT=1. Catalog browsing is available for read-only deployments. The wizard does not write single-file, Git-backed, or Swarm-config-backed settings; existing editing workflows for those modes are unchanged.

Installed templates cover local Docker, Docker through SSH, Swarm through SSH, SSH host metrics, Grafana, Prometheus and a custom HTTP JSON API. Each HTTP template also has an SSH-tunneled variant. These connect to existing systems; they do not provision Docker engines, Swarm clusters or monitoring servers. SSH keys, known_hosts and optional bearer-token files must already be mounted in Declarack. HTTP bearer/basic credentials require HTTPS, as they do for manually configured targets.

Generated operation and feature IDs use the new target ID as a namespace, allowing multiple copies of an integration. Existing targets, files, operation definitions and feature definitions are never overwritten. Sequential default filenames such as zz-integrations/000001-staging.yaml preserve the order of successive additions. If another later source overrides the target or environment membership, review fails with a filename-ordering error rather than silently losing the new target.

Review/save use the source revision and a digest. Any intervening source edit requires a fresh review. Saving does not reload configuration or run deployment operations. A failed connection test can still be saved for an offline target. Installed templates select named credentials from Settings → Credentials; profiles can hold entered values or mounted file references. The generated fragment remains ordinary editable configuration.

Supply a new template¶

An adapter manifest can list template files:

integration_templates: [integration-templates.yaml]

Those files contain an integration_templates mapping, just like adapter operation and feature files. Trusted system configuration can also add templates under the same top-level key. Duplicate IDs are rejected. Changes to deployment-managed single-file template definitions follow the same restrictions as operation/feature definitions; folder configuration authors can edit their source files and reload.

Here is a complete additional template fragment, using the installed Docker adapter:

integration_templates:
  company.docker-readonly:
    title: Docker inventory
    description: Start with a small inventory view of an existing engine.
    fields:
      - key: socket
        label: Mounted Docker socket
        default: /var/run/docker.sock
        required: true
        pattern: '^/'
    document:
      targets:
        '{{id}}':
          label: '{{label}}'
          connection: docker_socket
          socket: '{{socket}}'
          features: [disk_usage]

id and label are common fields supplied by the framework; environment placement is handled separately. Template fields support text, number, checkbox and static select controls, defaults, required, pattern, max_length, numeric min/max/integer, and JSONata syntax validation with format: jsonata. Up to 24 custom parameters are supported. Installed SSH presets demonstrate integer ports and mounted paths.

The document is a YAML/JSON tree. {{field}} as an entire value preserves the parameter's type. Embedded placeholders interpolate text, including mapping keys such as {{id}}.resources. YAML is serialized after expansion; parameter text is never evaluated as YAML, shell commands or JavaScript. Empty optional mapping values are omitted; false and 0 are preserved. A template must create exactly the requested target ID. It may additionally add namespaced operations, features, pages, checks or batches. It cannot modify auth or configuration-storage settings.

Installed definitions are examples under backend/adapters/{docker,swarm,ssh,http}/integration-templates.yaml. Templates are trusted configuration, not remotely downloaded packages or an installer mechanism. The HTTP API preset supplies a generic one-column JSON view; customize the saved feature columns, actions and mappings in YAML to fit the actual API.

API endpoints use existing application authentication/action-request protection:

  • GET /api/v1/settings/integrations: templates, environments and source revision.
  • POST /api/v1/settings/integrations/preview: validate and return generated YAML.
  • POST /api/v1/settings/integrations/test: validate and probe the draft target.
  • POST /api/v1/settings/integrations/save: revalidate and create the new file.

POST bodies contain template, values, optional environment/path, and revision. Save also requires the reviewed digest.

Dynamic select fields¶

Use options_from on a workflow select field:

- key: image
  label: Image
  type: select
  required: true
  allow_custom: true
  options_from:
    operation: images.list
    rows: '$distinct(RepoTags[$ != "<none>:<none>"])'
    value: '$'
    label: '$'
    limit: 200

The standalone container form uses this image picker and an optional primary network picker. A blank network keeps Docker defaults or advanced create options. The selected network is mapped into HostConfig through workflow JSONata, not JSX. Image loading does not pull an image or start a container.

options_from.operation must be a declared inventory, selector, detail or related read with a binding compatible with the workflow target. The workflow grants this read without requiring its resource to appear in navigation. Actions are refused as option sources. Config authors remain responsible for assigning genuine reads as inventory operations: an arbitrary external command/API cannot be proven read-only by its name. Manual/on-demand inventory requires manual: true, which shows an explicit Load options button and never auto-collects after dependency changes.

rows maps the operation result. value and label map each returned row. Values must be unique strings or safe integers; the select submits strings. Duplicate identities produce an error. The default limit is 200, configurable from 1–1000; truncation is shown in the UI. Refresh options explicitly re-reads the source. Without allow_custom, unavailable values/loading errors prevent selecting an invalid choice. Existing values remain visible, never silently replaced by the first option. allow_custom: true offers suggestions and permits manual text when an API is unavailable or an existing value is not returned.

Dependent fields¶

Inputs are JSONata expressions evaluated against the workflow context (form, entry, provider, creating, results). Declare parent fields explicitly:

fields:
  - key: project
    label: Project
    type: select
    required: true
    options_from:
      operation: projects.list
      rows: items
      value: id
      label: name
  - key: deployment
    label: Deployment
    type: select
    required: true
    options_from:
      operation: deployments.list
      depends_on: [project]
      inputs:
        project_id: form.project
      rows: items
      value: id
      label: name

The example operation names must be defined as compatible reads in your own features. Missing parent values block collection. Changing a parent clears its transitive dependents and invalidates reviewed results. Reset maps also clear fields depending on the values they change. Unknown parents and dependency cycles are rejected at configuration load. Query input changes start a fresh read; unrelated edits do not restart an identical request. Aborted or stale responses cannot replace options for a newer query. Form unmount cancels browser reads; it does not promise to cancel work already running on the remote system.

Scalar validation is shared with the setup form: required values, choices, patterns, lengths, finite numeric bounds/integer constraints and optional JSONata syntax. Zero and false remain valid values. These are authoring/UX checks; operation schemas and adapter validation remain authoritative for actual changes.
