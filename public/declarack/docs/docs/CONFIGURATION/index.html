Declarack configuration guide¶

New to the model? Read How configuration fits together for diagrams, an example and the edit/review/save/reload workflow.

Declarack's main YAML is the system configuration. It describes the environments Declarack connects to, the capabilities it exposes, the operations it can execute, how their results appear, and the installation's authentication. A dashboard layout is one part of that configuration.

The existing filename dashboard.yaml, environment variable DECLARACK_CONFIG, Python class Dashboard, and Settings terminology remain supported. This guide uses “system configuration” to describe their scope; it does not rename those interfaces.

The configuration layers¶

Layer Examples Where it lives
Deployment/bootstrap Port mapping, socket/host mounts, config source, process environment, Docker secrets Docker Compose, Swarm service spec, environment variables
System configuration Targets, environments, views, operations and auth references Active database revision; DECLARACK_CONFIG supplies import/export source documents
Adapter definitions Connection/executor code, built-in operations and UI definitions backend/adapters/*, optional mounted adapter packages
Application source An application's Compose YAML, GitHub repository/ref, stack deployment inputs Saved source records, mounted folders, GitHub
Runtime state Administrators, sessions, login limits, saved stack metadata/PATs, Compose sources, browser table preferences, terminal sessions Database, data directory, browser storage, process memory

The system config does not replace an application's Compose file or the Docker daemon's daemon.json. It does not continuously reconcile container state. Its operations run when requested; enabling a feature is not a command to deploy an application. An HTTP environment is just as valid as a Docker environment.

Start with the included configuration catalog for Docker, Swarm, SSH, Prometheus, or Grafana. See health checks for current health integrations, persisted checks and notification limits. Upgraders should read the Declarack rename guide.

The main file has these recognized top-level sections:

targets: {}           # Required: at least one connection
operations: {}        # Optional: additional named operations
features: {}          # Optional: additional UI features
credentials: {}       # Named inline/file-backed credential profiles
pages: {}             # Optional: custom pages querying multiple targets
environments: {}      # Optional: groups of targets
checks: {}            # Optional: scheduled read/connection checks
batches: {}           # Optional: multi-target operation pages
integration_templates: {} # Optional: trusted setup templates
# auth: ...          # Optional: local account bootstrap and session settings
# legacy_workspace: production

Built-in operations and features are loaded from adapters before custom definitions. Custom names must be unique: system config adds definitions; it cannot override a built-in definition with the same ID. Enable only the desired features per target.

Database authority and file synchronization¶

The active system configuration lives in the database. YAML files seed an empty installation and remain explicit import/export sources. GUI saves create a saved database revision; Activate configuration updates the active revision. On restart, the active revision is loaded, not pending saved changes or edited files. DECLARACK_CONFIG_FORCE_LOAD=1 imports the configured source on every startup; DECLARACK_CONFIG_WRITE_BACK=1 writes local files before GUI activation. Both default to off. GUI editing defaults to enabled; disable it with DECLARACK_CONFIG_EDIT=0. See configuration authority and recovery for exact flag combinations, publication providers and write-back recovery.

Loading and validating configuration¶

Without DECLARACK_CONFIG, Declarack generates a single local Docker target. It checks the Docker socket to choose Swarm or standalone features. If that check fails, the current fallback assumes Swarm; use an explicit file to remove ambiguity. The Settings editor is available only when an explicit config file was loaded.

With a file, Declarack loads exactly the targets in that file; it does not add the automatic local target. Mount the configuration and all referenced paths into the container, then set the environment variable. For the repository's compose.yaml, a small override can be:

# compose.config.yaml; paths assume this file is in the repository root.
services:
  declarack:
    environment:
      DECLARACK_CONFIG: /etc/declarack/dashboard.yaml
    volumes:
      - ./docs/examples/http-environments.yaml:/etc/declarack/dashboard.yaml:ro

# Set DECLARACK_PASSWORD in your shell or deployment environment first.
docker compose -f compose.yaml -f compose.config.yaml up -d --build

The base Compose deployment supplies its existing socket and data mounts. Change the example API addresses before using those environments. Settings load at startup. Local files and folders can also be explicitly reloaded from top-level Settings after external edits. Reload validates before swapping the running model; invalid changes retain the previous model. Authentication and legacy-workspace changes still need restart. There is no automatic file/Git watcher. See the folder merge/reload guide for exact rules and limits.

For a local schema check from the repository, with backend dependencies installed:

python - <<'PY'
from backend.server import load_dashboard
config = load_dashboard("docs/examples/http-environments.yaml")
for target in config.public()["targets"]:
    print(target["id"], target["provider"])
PY

This loads trusted adapter Python and validates references and executor definitions. It does not execute inventory operations or prove upstream connectivity. Credential files referenced by the configuration must exist even for validation. JSONata expressions are evaluated in the frontend; startup validation checks required field shapes, not every expression's syntax or every UI option.

General rules:

  • YAML files are limited to 1 MiB. Swarm config saves have a stricter 500 KiB limit.
  • Duplicate YAML keys fail validation. Merge into existing top-level mappings.
  • IDs for targets, features, operations, and adapters start with a lowercase letter, followed by lowercase letters, digits, _, ., or -; maximum length is 80.
  • Labels and titles are human-readable and may contain spaces/capitalization.
  • Paths refer to the filesystem inside Declarack, unless a particular setting explicitly identifies a remote or worker-host path.
  • The YAML loader does not perform environment substitution, includes, or shell expansion. ${TOKEN} in this YAML is a literal string. Docker Compose's own ${...} substitution applies to deployment Compose files, a separate layer.

Configuration folders¶

A folder is one large recursive configuration merge, not a collection of separate apps. Files load in relative filename order, mappings merge, and later scalars/lists replace earlier values. Use CONFIG_FOLDERS.md for source browsing, manual reload, a working example, and the current local-storage-only boundary.

Root environment and navigation¶

Use Settings → Home & environments for a form editor backed by the same YAML review/save/reload workflow. See the environment editing guide.

environments.root is the reserved Home environment and always exists. Configure its label, pages, batches, targets and ordered navigation just like other environment placement. Root defaults to no targets or batches and all custom pages. An explicit root pages list replaces the default. Built-in installation tools can be ordered, grouped, renamed or hidden through root navigation; Settings remains installation-wide. See page and fleet placement for the complete schema and example. The former page top_level flag is removed.

Targets and connections¶

A target is a named environment. Its connection selects an adapter; that adapter reports a provider used to choose operation bindings.

Connection/settings Selected provider Purpose
docker_socket, no swarm or swarm: false docker_standalone Standalone Docker engine
docker_socket, swarm: true docker_swarm Swarm manager
ssh ssh Commands/collectors on an SSH host
http http An upstream API

Common target keys are label, connection, and features. features is an ordered list of enabled feature IDs, not inline feature definitions. Navigation preserves that order within feature groups. Feature lists must match available bindings; enabling Swarm configs/secrets on standalone Docker fails validation.

Built-in feature availability¶

Feature IDs Compatible providers / scope
overview, services, nodes, tasks, stacks, configs, secrets Swarm manager
compose, images, disk_usage Standalone Docker
containers Standalone engine or the connected Swarm manager's local engine
networks Connected standalone/Swarm engine, with Swarm references where available
volumes Standalone engine or node-local Swarm jobs; automatic inventory on page open; explicit size collection
host_metrics Swarm node jobs or SSH host; manual collection

Resource-specific behavior and current action coverage are documented in DOCKER_ACTIONS.md. This list does not imply every Docker CLI flag is exposed by every feature.

Local Docker and Swarm¶

targets:
  lab:
    label: Local Docker
    connection: docker_socket
    socket: /var/run/docker.sock
    features: [compose, containers, images, networks, volumes, disk_usage]
  production:
    label: Production Swarm
    connection: docker_socket
    socket: /run/production-docker.sock
    swarm: true
    agent_image: registry.example.com/declarack@sha256:REPLACE_WITH_IMAGE_DIGEST
    host_metrics: true
    worker_socket: /var/run/docker.sock
    metrics_disk_path: /var/lib/docker
    features: [overview, services, nodes, tasks, stacks, configs, secrets, networks, volumes, host_metrics]

These socket paths must already be mounted or otherwise supplied. Defining two targets pointing at one socket does not create two independent environments.

Docker target key Meaning
socket Absolute Unix socket path inside Declarack; mutually exclusive with ssh_tunnel
swarm Boolean, default false; Swarm operations require an active manager
agent_image Same Declarack image available to worker nodes, preferably pinned by digest
host_metrics Enable Swarm host-metric jobs; enabling the feature alone is insufficient
worker_socket Docker socket on each worker host, default from runtime settings
metrics_disk_path Absolute worker-host path whose filesystem capacity is measured
stack_root Mounted source-folder root; falls back to DECLARACK_STACK_ROOT, then /stacks
host_root Optional host filesystem mapping for viewing reported Compose source files

Swarm node-local work uses short-lived jobs pinned to nodes. The manager reads the results and removes jobs. It never SSHes into individual workers. Remote terminals also use temporary Swarm relay jobs, not worker SSH. See action coverage.

Remote Docker or Swarm through a manager tunnel¶

targets:
  remote_swarm:
    label: Remote production
    connection: docker_socket
    swarm: true
    ssh_tunnel:
      host: manager.example.com
      port: 22
      remote_socket: /var/run/docker.sock
      credential: tunnel_remote_swarm
    agent_image: registry.example.com/declarack:YOUR_VERSION
    features:
    - overview
    - services
    - nodes
    - tasks
    - stacks
    - configs
    - secrets
    - networks
    - volumes
credentials:
  tunnel_remote_swarm:
    type: ssh
    username: declarack
    private_key:
      file: /run/secrets/manager_ssh_key
    known_hosts:
      file: /etc/declarack/known_hosts

The tunnel forwards the manager's Unix socket to a temporary local socket. Declarack supervises/reconnects the SSH process. The SSH user needs access to the remote Docker socket. Identity and known-hosts files must exist in Declarack; host-key verification is enabled. port defaults to 22 and remote_socket to /var/run/docker.sock. Use swarm: false and standalone features for a remote standalone engine. This is distinct from connection: ssh below.

SSH host¶

targets:
  backup:
    label: Backup host
    connection: ssh
    host: backup.example.com
    port: 22
    features:
    - host_metrics
    credential: ssh_backup
credentials:
  ssh_backup:
    type: ssh
    username: declarack
    private_key:
      file: /run/secrets/backup_ssh_key
    known_hosts:
      file: /etc/declarack/known_hosts

The SSH adapter executes configured commands on that host. The built-in metrics collector requires remote python3; it is manual and does not supply an automatic environment summary. A custom inexpensive SSH operation can supply a summary.

HTTP API¶

targets:
  inventory:
    label: Inventory API
    connection: http
    base_url: https://inventory.example.com/api
    features:
    - asset_inventory
    credential: token_inventory
credentials:
  token_inventory:
    type: token
    token:
      file: /run/secrets/inventory_token

base_url may have a path prefix. A binding path /assets is appended to it, giving https://inventory.example.com/api/assets. Userinfo, query strings, fragments, and whitespace are not accepted in base_url. Bearer credentials require HTTPS. An optional ssh_tunnel block uses the same SSH host/user/identity/known-hosts settings as manager tunnels, with remote_host and remote_port for the TCP upstream. They default to the URL host and HTTP/HTTPS port. The URL remains the HTTP Host/TLS identity; SSH forwards through a private local Unix socket. Direct HTTP behavior is unchanged when the block is absent. HTTPS certificate checks and the HTTPS requirement for bearer credentials remain in effect. Settings connection tests isolate temporary forwards; removed target forwards are retired on apply. See the running multi-environment lab for direct/tunneled Grafana and Prometheus configurations.

The adapter does not follow redirects. Requests default to JSON responses, have a 15-second upstream timeout, and a 2 MiB response limit. Arbitrary custom headers, OAuth login flows, and configurable TLS client certificates are not implemented.

Operations, bindings, and inputs¶

An operation is a named backend capability. A feature invokes its ID; the target's provider selects a binding; the binding's executor performs the work.

operations:
  assets.inspect:
    bindings:
      http:
        executor: http.request
        method: GET
        path: /assets/{id}
        query:
          include: details
        inputs:
          id: {type: string}

bindings must be nonempty. A target exposes only the operations referenced by its enabled features, actions, selectors, detail views, workflows, or related resources. A registered operation is not automatically callable on every target. This is an installation capability boundary, not per-user role-based authorization.

Dispatch API¶

The UI calls POST /api/v1/targets/TARGET/operations/OPERATION/run with the input mapping as its JSON body. The response wraps executor output as {"result": ...}; JSONata feature expressions receive the inner result. State-changing HTTP requests to Declarack require X-Declarack-Action: 1, the session cookie and X-Declarack-CSRF from the auth snapshot, even when the configured upstream operation is a read. Cross-site action requests are rejected. GET /api/v1/targets exposes feature metadata to authenticated users, not connection credentials. These endpoints dispatch registered capabilities; they do not accept ad-hoc URLs, commands, or feature definitions from callers.

Request executors¶

http.request and docker.request share path, method, query, body, and inputs. HTTP calls use the target's configured API; Docker calls use the selected engine. Methods are GET (default), POST, PUT, PATCH, and DELETE.

  • path starts with /; no origin override, dot segments, query, or fragment.
  • {name} placeholders refer to declared required inputs. Path values are encoded as individual path segments; query values are URL-encoded separately.
  • body recursively substitutes string templates. An exact '{count}' preserves the input's JSON type; 'prefix-{count}' produces a string.
  • Literal braces in templates need Python-format escaping ({{ and }}). Prefer a YAML mapping for a JSON body rather than embedding a JSON document in a string.
  • Optional inputs cannot appear in these templates: absent inputs have no implicit default. Define separate operations when request shapes differ.
  • http.request supports output: json (default), json_lines, or text through the shared decoder. Text becomes {text: ...}; JSON lines become {items: [...]}.
  • docker.request can use fields to project top-level fields and output: docker_logs to decode Docker's log framing. Its specialized projection modes are used by built-in service/node views; prefer full responses for custom views.

Input types¶

All fields are required unless required: false. Unknown supplied fields fail.

Type Validation
string Up to 512 characters, no NUL
text Up to 700 KiB encoded text, no NUL
integer Actual integer; min/max default to 0/1000
boolean Actual boolean, not the strings "true"/"false"
choice String in the declared nonempty choices list
list Array with at most 20 items; executor supplies any item-level checks

label supplies a human-readable action-form label. Backend schemas and executor validation remain authoritative regardless of UI confirmation or field visibility.

Command and specialized executors¶

Executor Binding-specific settings
ssh.exec Fixed command argument list, output; optional built-in script: host_metrics
swarm.exec command, output, mount_profile, all_nodes, write, inputs.node_id
swarm.update Built-in version-aware service/node updates via action
swarm.workflow Registered coordinating workflow selected by handler
docker.volumes Built-in volume operations selected by operation
docker.compose Built-in Compose actions selected by action
docker.pull Validated image pull using its reference input
docker.terminal, swarm.terminal Session lifecycle selected by operation

Command templates substitute declared inputs into an argument list, not a local shell command string. SSH quotes those arguments for the remote shell. The first argument must be a fixed executable. These definitions are trusted: choosing a shell/interpreter explicitly still gives the configured code its normal authority. Command output modes are json, json_lines, text, and agent_json; results are bounded to 2 MiB. Specialized executors accept their own registered actions, not arbitrary new workflow names. Consult their bundled YAML for exact input schemas.

Swarm job mount profiles are docker_socket, host_metrics, or none. All-node jobs use all_nodes: true with string node_id (including all); single-node jobs use type: string with pattern: '[a-z0-9]{12,64}'. all_nodes with write is rejected. All-node reads have bounded fan-out and return per-node results/errors. Setting operation-level on_demand: true makes the normal feature manual; detail operations and environment summaries cannot use on-demand operations.

Features and the UI renderer¶

A feature combines an operation with a generic presentation. It can be a table, a card overview, or a detail/creation workflow. The target chooses which features are visible; feature definitions themselves live at the file's top level or in an adapter.

features:
  asset_inventory:
    title: Assets
    group: Workspace
    operation: assets.list
    rows: items
    columns:
      - {label: Name, value: name, truncate: true}
      - label: State
        value: state
        badges: {ready: active, failed: destructive}
      - label: Size
        value: '$string($round(bytes / 1000000, 2)) & " MB"'
        sort_value: bytes
        optional: true
    details:
      operation: assets.inspect
      row_id: id
      input: id
      title: name
      fields:
        - {label: Name, value: name}
        - {label: Attributes, value: attributes}

This fragment requires matching assets.list/assets.inspect operations and a target that enables asset_inventory. The full example includes every required section.

Feature field Behavior
title Page/navigation label
group Sidebar heading; defaults to Workspace
group_by_provider Provider-to-heading mapping overriding group
operation Inventory/overview operation ID
rows JSONata selecting table records, default $
columns Ordered table columns
manual Do not automatically collect ordinary inventory on entry
selector Resource selector mapping: lookup operation, input binding, labels and JSONata row/value/text expressions
details Dedicated detail route, operation, identity mapping, fields
cards, panels Dedicated overview-page presentation
environment Cards contributed to the combined Environments page
actions, workflow Action controls and optional source/lifecycle forms
children, related On-demand expanded rows / associated-resource sections

description is forwarded to the frontend but is not a universal page subtitle. Not every forwarded metadata field has visible behavior in every renderer mode.

Columns, details, and overview panels¶

Column value is a JSONata expression evaluated against one selected row. sort_value optionally provides a raw numeric/string sorting key, independent of formatted text. badges maps exact returned strings to active, muted, or destructive. truncate shortens long values visually. optional starts a column hidden; optional_by_provider can override that per provider.

The first visible column links to details when the row has details.row_id. details.input names the backend argument receiving that ID; details.title is a dotted result path. Detail fields use JSONata against the complete detail response. Nested values can be expanded in the shared structured-value inspector.

Ordinary tables search all mapped columns before frontend sorting and pagination. Page-size choices are 10, 25, 50, 100, and 250. Density, hidden columns, and main-table page size are browser preferences, not configurable system defaults. These controls do not implement upstream pagination: the operation still fetches its configured result.

Feature-level cards calculate value and optional caption against the whole response. A feature destination links within that target when enabled. Built-in overviews use tone names such as mint, blue, purple, and amber for styling. panels declare title, feature, JSONata rows, row_id, columns, and optional wide. Panel column tone is a JSONata expression that can return destructive. These overview cards differ from the environment.cards schema below.

Current collection inputs are intentionally limited: automatic inventory takes no inputs except the renderer's supported node_id picker; a detail page supplies its one declared identity argument. Arbitrary multi-input search forms should use an action/workflow rather than assuming generic inventory filters exist.

Three different expression mechanisms¶

Location Mechanism Example
Rows, values, captions, summary tones, related inputs JSONata $count(items[status = "healthy"])
Request/command templates Declared input substitution /applications/{id}
Workflow bind, needs, disabled, when keys Dotted context paths form.name, results.preview.digest

Workflow when/locked rules compare values for exact equality. They are not JSONata conditions. A workflow bind value is a context path, not an arbitrary expression. Quoting expressions in YAML helps preserve punctuation, colons, and strings.

Environment summaries¶

The home route #/environments gathers summaries from all configured targets. An enabled feature opts in using environment.cards and its existing operation:

environment:
  cards:
    - {label: Applications, value: '$count(items)'}
    - label: Unhealthy
      value: '$count(items[status != "healthy"])'
      caption: '"Current inventory"'
      tone: '$count(items[status != "healthy"]) > 0 ? "destructive" : null'
      feature: applications

value, caption, and tone are JSONata evaluated against the entire operation result. feature is an optional destination feature ID, not an expression. A destructive tone highlights the value. Current environment cards do not offer arbitrary color palettes or chart types. Captions describe returned data; historical comparison requires the operation to supply historical data.

Summary operations must have no inputs in their bindings and cannot be manual or on demand. Use inexpensive reads: the core does not independently prove a custom operation is read-only. Enabling a summary explicitly allows its operation to run on page entry or refresh.

Collection is bounded to four concurrent requests across cards, with a 15-second client timeout per request. Refresh can be global or per environment. There is no background polling. Client cancellation does not guarantee cancellation of remote work already in progress. Built-in summaries do not start host metrics/volume jobs.

Status Meaning
Checking At least one summary is pending
Loaded All configured summaries succeeded; not a workload-health guarantee
Partial Some summaries succeeded and some failed
Unavailable All attempted summaries failed; not a definitive host reachability test
No summary No eligible summary configured; workspace links remain available

Standalone summaries are supplied by enabled Compose, container, and image features. Swarm's overview feature supplies service/node/stack/replica summaries. If local containers is enabled on a Swarm target, it also contributes engine-local container counts; those are not cluster-wide container counts. The same custom feature can summarize multiple HTTP or SSH environments without JSX changes.

Custom cross-target pages¶

Top-level pages definitions combine named operation sources across targets, with JSONata cards and tables using their shared results. They reuse existing target permissions and keep manual collectors on demand. Unlike per-target features, they can calculate totals or join rows from multiple environments. Read the custom pages guide and the complete operations dashboard preset.

Actions and workflows¶

Table and detail actions¶

actions:
  - label: Restart application
    operation: applications.restart
    icon: restart
    help: Ask the application API to restart the selected application.
    row: {id: id}
    confirmation: Restart this application? Expect a brief interruption.
    variant: destructive

This example maps the row's id to backend input id. Other required inputs from the operation schema appear in the shared action form. row values are direct record keys, not JSONata or dotted paths. detail: true places an action in detail view instead of its list location. Without row or detail, it is a page-level action.

Action field Behavior
label, icon, help Visible/accessibility label, icon, tooltip
confirmation Shared confirmation modal before submitting
variant Button style: usually outline or destructive
immediate Execute directly; do not use for actions requiring confirmation
output: json Full JSON inspector, unmasked
output: FIELD Display the named result field as text
output: '$' Show the serialized whole result in the ordinary action renderer
presentation: {placement: row, viewer: json} Inline result beneath the originating row; also supports page/dialog and structured/text
result: replace Replace displayed inventory with action result
back Return to the list after a detail action
enabled_when JSONata against a list row to enable/disable its action
disabled Direct row key whose truthy/nonempty value disables the row action
requires Dotted result path required for showing a detail action
hidden Hide action from ordinary controls (for supporting operations)

See action output placement and viewers for stable row identity requirements, loading/error behavior, examples and placement restrictions.

Action icons currently include json, play, stop, pause, restart, trash, plus, tag, edit, terminal, logs, activity, network, and settings. The terminal configuration object wires a feature to the session renderer; use existing container/task definitions as the reference for its operation IDs and identity mapping. An icon alone does not enable a terminal.

Confirmations and disabled controls are UI behavior, not extra backend authorization. Executors must validate destructive inputs and enforce their own prerequisites.

Workflow forms¶

A workflow uses a dedicated create/detail page for coordinated forms. Source settings and lifecycle actions can be separated using named sections.

workflow:
  create_label: New item
  defaults: {name: ''}
  sections:
    - {id: source, title: Source}
    - {id: deployment, title: Execution}
  fields:
    - key: name
      label: Name
      required: true
      changes_source: true
      section: source
  actions:
    - label: Save
      operation: items.save
      bind: {name: form.name}
      validate: true
      open: name
      reload: true
      primary: true
      section: source

This is a schema illustration; items.save must be defined before use. create_only: true limits the workflow to creation. Without it, details can render the workflow. defaults are merged with the current detail entry to initialize the form. summary fields use JSONata against the entry. readout can display an entry's text field or a downloadable base64 field; see config/secret feature definitions.

Workflow field options:

Field Meaning
key, label, section Form key, visible name, section ID
type Native input type or textarea, select, checkbox, file, selection
required, description, rows Validation hint, explanatory text, textarea height
choices For select: mapping of stored values to labels
when Equality rules against context paths; visibility
locked Equality rules against context paths; disable editing
changes_source Mark dirty and invalidate stored operation results
reset, reset_results Merge reset values into the form; discard named stored results when reset is applied
source, warnings, item_label, empty, limit Context paths/options for a selection list

File inputs encode up to 500 KiB as base64. Selection fields return selected item objects; specialized executors validate them. Sections must match fields/actions' section values. Without sections, omit the section key on fields/actions too.

Workflow action options:

Field Meaning

clean Disable until source changes have been saved

The context contains form, original entry, boolean creating, stored results, and provider. Hidden form fields are omitted from form-bound inputs. Workflow output is a named field; unlike ordinary actions, it is not a special JSON inspector switch. Built-in stack/Compose workflows require preview digests in the backend as well as in their UI; copying needs alone does not implement that guarantee.

Related resources and child rows¶

related renders associated resources on workflow detail pages. children renders expandable inventory rows and child sections on ordinary details. Both use the shared resource renderer and declare their own operation:

related:
  title: Application resources
  operation: applications.resources
  inputs: {id: id}
  sections:
    - title: Containers
      rows: containers
      row_id: Id
      open: true
      columns:
        - label: Name
          value: '$join(Names, ", ")'
          feature: containers
          row_id: Id
        - {label: State, value: State}

Related inputs values are JSONata against the parent entry. Each section selects rows from the related operation's result. Column feature and row_id link to a destination only when that feature is enabled. route_prefix supports special routes such as terminal identities; link_when is JSONata against the child row. Sections can declare nested children using the same model. Related collection runs when its detail section or expanded row mounts and on explicit refresh. Avoid expensive operations here because these sections are not inherently manual.

Related tables provide their own search/sort/paging. Unlike main-table columns, the current related renderer sorts displayed mapped values; sort_value does not supply an alternate key there. See the built-in Compose and stack definitions for real associated-resource schemas.

A complete HTTP integration¶

examples/http-environments.yaml is a complete, loadable system configuration containing:

  1. Local Docker with built-in features.
  2. Staging and production API targets reusing one custom feature.
  3. List/inspect/restart HTTP operations and typed inputs.
  4. A table, detail page, JSON inspector, confirmation action, and environment cards.

Its upstream API contract is:

GET  /applications              -> {"items": [application, ...]}
GET  /applications/{id}         -> application
POST /applications/{id}/restart -> successful JSON response, or empty success response
                                  body: {"reason": "operator-entered text"}

An application record looks like:

{
  "id": "website",
  "name": "Website",
  "status": "healthy",
  "version": "1.4.2",
  "owner": "Platform team"
}

This contract is illustrative; Declarack does not supply the example upstream APIs. Adapt paths and JSONata to your real API. No new adapter is needed for these HTTP calls. The restart button sends the configured request; the upstream implements what “restart” actually does.

Settings editing and storage¶

The Settings page reads the selected authoritative source, validates proposed YAML, and can test a target connection. Writes require the revision returned by the last read. A conflict requires reloading rather than overwriting another change.

What can be edited in Settings today?¶

Target definitions can change through Settings, subject to storage permissions and normal validation. Changes to top-level operations, features, auth, and legacy_workspace are rejected by FileSettings.validate. The target named by legacy_workspace is also protected from Settings edits. This restriction applies to the existing single-document editor, validation, connection testing, and saving in all three storage modes. Folder-backed New file instead validates the full merged model and supports new execution/UI definitions; see the folder guide.

Execution and UI definitions can still be changed in the source file/folder through deployment, then applied using local Reload configuration. Authentication and legacy-workspace changes require restart/redeploy. “Configuration alone” means no Python/JS changes; it does not currently mean every definition can be changed through the browser editor.

The restriction is an implementation guardrail, not a YAML requirement. Custom operations may execute privileged commands or requests using the application's credentials. Authentication and some legacy-workspace globals are initialized at startup rather than safely hot-reloaded. A future full-config editor would need explicit lifecycle/restart behavior and broader validation. Target editing is also privileged; the present division is not a complete security boundary or per-user permission system. The current code does not offer a toggle to lift this restriction.

File storage¶

DECLARACK_CONFIG=/etc/declarack/dashboard.yaml
DECLARACK_CONFIG_STORE=file
DECLARACK_CONFIG_EDIT=1

file is the default store. Without DECLARACK_CONFIG_EDIT=1, Settings is read-only. With it, supported changes replace the validated file atomically, retain the previous content as dashboard.yaml.previous, and update the running target model. Mount the enclosing directory writable, not a single bind-mounted file, for atomic replacement. This enables supported Settings edits, not unrestricted edits to execution definitions or auth. External file changes can use Reload configuration; authentication and legacy changes need restart.

GitHub storage¶

DECLARACK_CONFIG=/etc/declarack/dashboard.yaml
DECLARACK_CONFIG_STORE=git
DECLARACK_CONFIG_GIT_REPO=your-org/your-config-repo
DECLARACK_CONFIG_GIT_BRANCH=main
DECLARACK_CONFIG_GIT_PATH=declarack/dashboard.yaml
DECLARACK_CONFIG_GIT_TOKEN_FILE=/run/secrets/config_git_token

Runtime startup still reads the local mounted file. Settings reads the configured GitHub branch/file. Saving creates a branch, file commit, and pull request; it does not merge the PR, pull the file into the container, or replace the running config. Your deployment pipeline must deliver the merged file and redeploy. Keep the mounted file and Git source aligned. Without a token, storage is read-only and only works where GitHub permits unauthenticated reads. This implementation is GitHub-specific, not a generic Git remote or repository watcher.

Swarm config storage¶

DECLARACK_CONFIG=/etc/declarack/dashboard.yaml
DECLARACK_CONFIG_STORE=swarm
DECLARACK_CONFIG_SERVICE=your-stack_declarack
DECLARACK_CONFIG_SOCKET=/var/run/docker.sock
DECLARACK_CONFIG_MOUNT=/etc/declarack/dashboard.yaml

The named service must mount a Swarm config at DECLARACK_CONFIG_MOUNT. Settings reads that attachment through the selected manager socket. Saving validates the revision, creates a versioned Swarm config, and updates the service's config attachment. Swarm then redeploys Declarack. The old config remains available for Docker rollback; there is no automatic config-pruning policy. Keep your external deployment specification aligned so a later stack deploy does not restore an old attachment. The settings socket is separate from targets' connection definitions.

Authentication and credential files¶

Connection credentials and optional first-account bootstrap use named credential profiles, including mounted-file references. The GUI manages profiles under Settings → Credentials and database login accounts under Settings → Administrators.

auth:
  provider: local
  bootstrap_credential: declarack_login
  session_hours: 8
credentials:
  declarack_login:
    type: basic
    username: admin
    password:
      file: /run/secrets/declarack_admin_password

Installation authentication uses database-backed local administrators and cookie sessions. provider defaults to local; bootstrap_credential optionally selects a basic profile used only when the users table is empty. session_hours defaults to 8 and accepts integers from 1 to 168. Without a bootstrap profile, use DECLARACK_ADMIN_USERNAME (default admin) and either DECLARACK_PASSWORD_FILE or DECLARACK_PASSWORD to seed the first account. Later changes to those inputs do not rotate existing passwords, and an absent bootstrap password mount does not prevent existing users from signing in.

Settings → Administrators manages database accounts separately from YAML. All administrators have full installation, credential and workload access. There are no granular roles or per-target permissions. HTTP Basic Auth is unsupported; migrate provider: basic / credential to provider: local / bootstrap_credential, and migrate clients to cookies and CSRF headers. See administrators, recovery, sessions and TLS for the complete contract, deployment examples and upgrade steps.

A credential file must contain one nonempty value; a trailing newline is accepted, embedded newline/NUL is not. Secret references are filesystem paths, not Docker secret names or automatic Docker API lookups. Mount the secret first:

# Deployment Compose/Swarm fragment, not system YAML.
services:
  declarack:
    secrets: [declarack_admin_password]
secrets:
  declarack_admin_password:
    external: true

This fragment assumes the external Swarm secret already exists. Standalone Compose has its own file-backed secret mechanism; standalone Docker Engine does not provide Swarm secret/config resources. Feature bindings enforce that distinction.

Bearer tokens, SSH keys/known-hosts, outbound HTTP Basic credentials, administrator bootstrap profiles, and the GitHub Settings token are separate credentials with separate purposes. Ordinary target metadata sent to the renderer excludes connection settings, but authenticated Settings reads show the system YAML. JSON inspection intentionally shows the full unmasked resource data. Treat the system YAML and Settings editor as administrator interfaces. Credential rotation is not file-watched. Connection credentials that are cached require activation/restart; existing login accounts require an account password reset. Inline bootstrap profile values remain in configuration history and exports.

DECLARACK_CONFIG_FORCE_LOAD and DECLARACK_CONFIG_WRITE_BACK accept 0 or 1 and default to 0; see database configuration.

Explicit Docker targets require a socket or ssh_tunnel; they do not inherit a missing socket from DOCKER_SOCKET. Per-target agent_image, host_metrics, metrics_disk_path, worker_socket, and stack_root override runtime fallbacks. With legacy_workspace, several worker fallbacks are reassigned from that target during startup, so explicitly setting worker options on each Swarm target is the clearest multi-environment setup.

DECLARACK_COMPOSE_HOST_ROOT applies to local Docker targets; tunneled targets require an explicit host_root. A local mount cannot read another server's filesystem. On native Linux, the optional deployment override maps / read-only to /mnt/host. Docker Desktop/macOS uses /Users to /mnt/host/Users instead. See host source viewing and the two compose.host-files*.yaml overrides. Viewing a file neither imports it as deployment source nor changes the Compose project.

Deployment-only names in compose.yaml, such as DECLARACK_STACKS_DIR, are Docker Compose substitution variables, not separately read backend environment variables. Registry/build secrets belong to the image build workflow, not the system YAML.

Application sources and persistent state¶

The system config selects connections and capabilities; saved application sources are separate. Keep the data volume when you rely on GUI-managed sources.

State Current storage
Stack source metadata, last deployment/commit and legacy encrypted PATs Target-scoped documents in the shared database
Legacy PAT encryption key Binary document in the same database
Saved Compose source definitions and inline YAML Target-scoped database documents; working YAML materialized locally
Administrators, hashed sessions, login limits, checks, operation records and configuration revisions Framework database tables
Native TLS identity Generated files under <DECLARACK_DATA>/tls, or external certificate/key mounts; outside database transfer
Mounted-folder source files Configured/mounted stack_root; external to the database
Table density, columns, main page size Browser local storage
Terminal sessions and inventory snapshots In-memory/session state

SQLite defaults to /data/state.sqlite; PostgreSQL can be selected through DECLARACK_DATABASE_URL or DECLARACK_DATABASE_URL_FILE. See database storage and migration before upgrading an existing data volume. The import preserves historical source records and credential keys.

Named targets normally have separate logical database scopes. legacy_workspace uses the default legacy scope and bridges old bookmarks; it must name a configured Swarm target. Renaming target IDs does not automatically move stored records.

Swarm sources support inline YAML, mounted folders, general HTTPS/SSH Git sources with branch/tag/commit refs, and legacy GitHub-tag sources. General Git stores credential references; legacy PAT records remain encrypted in database documents. See source retrieval and credentials for exact storage, authentication and deployment behavior.

Standalone Compose currently supports saved inline and mounted-folder sources; it does not have the GitHub-backed stack source workflow. Reported Docker Compose file paths are discovery metadata until explicitly viewed through host_root or saved as a source. Lifecycle actions require saved sources and fresh preview digests.

Swarm config-backed system settings do not make all Declarack application state stateless. GUI-managed stack sources/PATs and saved Compose sources still need a persisted database. External source management can reduce that state, but the current implementation does not reconstruct all saved source metadata from Swarm configs.

Adapter packages and extension boundaries¶

Built-in packages are discovered under /app/backend/adapters in the image. Configured installations can also load packages from the optional extra root. Each package has a manifest, trusted Python entrypoint, and optional YAML files:

id: inventory
api_version: 1
entrypoint: adapter.py:register
depends_on: [http]
operations: [operations.yaml]
features: [features.yaml]

The package may register reusable connections/executors; YAML lists define named operations/features. Dependencies load first. Duplicate IDs, unknown dependencies, cycles, invalid package-relative paths, and unsupported API versions fail startup. Packages run in the server process; mounting one is equivalent to deploying trusted application code. There is no browser plugin installer or automatic dependency installation.
