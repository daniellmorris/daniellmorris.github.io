Reusable tables, bulk actions, refresh and charts¶

These capabilities belong to the framework. Features and adapters supply data, expressions, input schemas and operations; the renderer contains no resource-type switches. Built-in Docker/Swarm configurations demonstrate them, and custom HTTP or SSH features use the same definitions.

Inventory filters, exports and refresh¶

A feature or custom-page panel can define up to 12 filters. Each filter maps a row with JSONata, then compares its string value to the selected choice. Filters combine with text search and sorting. Empty selection means all values.

filters:
  - key: state
    label: State
    value: State
    choices: {running: Running, exited: Stopped, created: Created}

Inventory tables and custom-page panels export all currently filtered/sorted rows, including rows beyond the current page. CSV includes the visible columns (panel columns for custom pages). Values are quoted and spreadsheet formula prefixes are neutralized. JSON contains full mapped row objects with original value types; it is unmasked. Hidden columns affect CSV only. Exports are browser downloads and do not write application storage. Related-resource tables retain their existing UI.

Custom-page panels now have search, filters, sorting and page-size controls rather than truncating results permanently. Their limit remains the initial page size (1–100). Inventory selection supports up to 100 resources across pages. Select-all selects only the current page, within that cap. Refresh clears selection; auto refresh pauses while resources are selected.

Feature and page refresh_interval defaults to 0 (off), or can be 5–3600 seconds. The UI offers an independent, session-only interval selector. Hidden browser tabs start no new refreshes, missed ticks do not queue, and refreshes do not overlap. Inventory refresh pauses during actions, confirmation, bulk selection and loading. Detail editors and on-demand/manual features do not refresh automatically. Custom-page refresh collects only non-manual sources; manual metrics remain explicit. This is browser-driven polling, not a background scheduler. Checks remain separate.

Reviewed bulk actions¶

Opt existing row actions into bulk execution:

selection_key: id
operation: applications.list
rows: items
actions:
  - label: Restart application
    operation: applications.restart
    row: {id: id}
    enabled_when: state = "running"
    bulk: true
    confirmation: Restart these applications? Expect brief interruptions.

selection_key is a stable unique row field path, defaulting to details.row_id. Values must be strings or safe integers; map other identities to strings. Composite identities can be created by the feature's rows mapping: the built-in volume table uses node ID plus volume name. Bulk actions require a confirmation, row-bound inputs and a stable key. They reuse ordinary operation schemas/defaults; shared inventory inputs such as selected node scope supply matching action inputs. Actions needing additional user-entered values are skipped if their required inputs cannot be supplied. Terminals and file browsers cannot be bulk actions.

The browser submits selected keys and the action's operation name, not arbitrary execution definitions. The server verifies that the feature/action is enabled on the target, re-reads inventory, maps rows and checks enabled_when, disabled and operation arguments. Missing/ineligible resources are listed as skipped. Ambiguous inventory keys are rejected. The confirmation shows eligible count, keys and skips. Confirmation requires a digest of this preview; a fresh inventory read must still produce the same eligible inputs before execution starts.

Eligible operations execute sequentially once each, in selection order. A failed resource does not stop remaining resources. The parent run is failed if any step fails, and the Operations page preserves each result. Nested asynchronous runs are watched by their run ID (up to one hour); timeout does not cancel the child. There are no automatic mutation retries or bulk rollback. Inventory/action state can still change after preview: adapters/remote APIs must enforce their own constraints. A per-target/feature bulk lock prevents overlapping bulk runs of that feature; it does not lock external clients or every individual action.

Bulk execution uses the same durable run store and interruption rules described in operation plans. Closing the browser does not stop server execution. Normal mutations stop if their journal cannot be written; explicit recovery safety steps remain best effort when storage fails.

API routes (under existing authentication and action-request protection):

  • POST /api/v1/targets/<target>/features/<feature>/bulk/preview
  • POST /api/v1/targets/<target>/features/<feature>/bulk/run

Both receive {operation, keys, inputs}; run additionally requires digest and confirmed: true. Selection is limited to 100 keys and inventory to 10,000 rows.

Built-in opt-ins: container start/stop/restart/pause/resume/remove, image removal, network removal, volume removal, and service restart/removal. Docker still rejects in-use resources. Bulk availability follows enabled operations and target scope; it does not turn manager-local Docker operations into cluster-wide operations.

Multi-source dashboard charts¶

Custom pages can contain cards, panels, charts, or any combination. Chart rows receives {data, sources}, exactly like cards and panels. x and each series value receive one mapped row. For example:

pages:
  workloads:
    title: Workloads
    refresh_interval: 30
    sources:
      containers: {target: local, operation: containers.list}
      services: {target: production, operation: swarm.services.list}
    charts:
      - title: Workloads across targets
        type: bar
        sources: [containers, services]
        rows: >-
          [{"target":"Local Docker","count":$count(data.containers)},
           {"target":"Production Swarm","count":$count(data.services)}]
        x: target
        series:
          - {label: Workloads, value: count}
      - title: Service replicas
        type: bar
        sources: [services]
        rows: data.services
        x: Spec.Name
        series:
          - {label: Running, value: ServiceStatus.RunningTasks}
          - {label: Desired, value: ServiceStatus.DesiredTasks}

Sources must already be enabled inventory/detail/related reads. Existing target and environment page placement rules apply. type is bar or line; a page can have up to 24 charts, each with 1–8 series. limit is 1–200 (default 100), selecting the last mapped rows. Input order is preserved: sort timestamp rows in JSONata for line charts. wide: true spans both columns on wide screens. Native SVG tooltips show full labels/values. No new chart runtime dependency is needed.

Only finite numeric values are plotted. Missing/null/string values remain gaps, not fabricated zeros; unavailable sources show an unavailable state. Negative and zero values are supported. Charts show the returned snapshot/query data and retain no historical samples. To show time series, query a source that supplies history, such as a Prometheus range query. No DuckDB/log ingestion is implied.

The complete operations dashboard configuration includes two charts, filters, paging and an opt-in 30-second refresh interval.

Row action results¶

Use action output presentation to expand structured data, JSON or text beneath the originating row. Placement and viewers are configured in YAML and shared across adapters. Related-resource expansion remains separate.
