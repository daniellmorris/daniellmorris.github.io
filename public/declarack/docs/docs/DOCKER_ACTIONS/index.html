Docker GUI action coverage¶

Declarack exposes operations through adapter YAML, not resource-specific JSX. The table distinguishes implemented actions from candidates for broader Docker CLI coverage.

Resource Implemented Next useful actions
Containers (standalone) List/inspect, create stopped from a local image, start, stop, restart, pause/resume, rename, one-shot stats, logs, remove stopped container, interactive terminal Command/env/ports/mounts/restart-policy editor, CPU/memory limits, health details, process list, filesystem changes, copy files, recreate from saved definition
Images (standalone) List/inspect, local MB/GB sizes, pull by reference, add tag, non-force removal Registry credential references, push, build from Dockerfile/Git, import/export, history, explicit untag versus removal
Networks Per-node Swarm inventory/inspection, manager-routed mutations; list/inspect; standalone create local bridge, connect/disconnect by container ID, non-force removal IPAM/subnet/gateway configuration, overlay creation, labels, driver options, endpoint aliases
Volumes Inventory/attachments, create named local volume, remove unused volume; Swarm uses node jobs Inspect labels/options, driver configuration, backup/restore using short-lived jobs
Services (Swarm) List/inspect, scale, rolling restart, logs, remove Versioned edits to image/resources/placement/update policy, rollback, create from structured form
Nodes (Swarm) List/inspect, scheduling availability Labels, manager promotion/demotion, removal with quorum checks
Tasks (Swarm) List/inspect Correlated logs and troubleshooting links; tasks are scheduler-owned, not directly restarted
Stacks (Swarm) Source editor/preview/validation, deploy/update/prune/replace/remove and selected volume cleanup Registry credentials, deployment history and comparison
Configs/secrets (Swarm) Create, inspect metadata/usage, remove; config content viewing Rotation workflow updating service references; secrets cannot be read back from Docker
Engine/storage On-demand disk usage Version/info/events, filtered prune with a preview and explicit resource/data scope
Hosts (SSH) On-demand metrics Explicit allowlisted host actions; Swarm never SSHs to workers

Configured actions¶

An operation defines execution and validated inputs in backend/adapters/docker/operations.yaml. A feature defines its UI in features.yaml. For example:

- label: Pause container
  operation: containers.pause
  icon: pause
  help: Suspend all container processes without stopping them.
  confirmation: Suspend all container processes without stopping them.
  enabled_when: State = "running"
  row:
    id: Id

enabled_when is JSONata used for row-button availability. Docker still enforces actual state and in-use checks at execution time. icon, help, and variant control generic button presentation. Row buttons use accessible labels and native tooltips; detail and create-page buttons retain visible text. Destructive actions use variant: destructive and a modal confirmation showing the target resource. Dialogs focus Cancel initially, contain keyboard focus, and support Escape before execution. Creation uses dedicated pages. workflow.create_only keeps create forms separate from inspect pages.

Enabled features determine the backend operation allowlist. An action can be removed by overriding its feature definition in deployment configuration; hiding a button alone is not authorization. Internal terminal transport operations are explicitly listed as hidden feature actions so they remain part of that allowlist.

Interactive container terminals¶

Open Containers → Open terminal. Select /bin/sh, /bin/bash, or /bin/ash (it must exist in the image) and optionally an exec user. Connect runs docker exec -it against the selected target's Unix socket or managed tunnel. The default user is the container's configured user, with no privileged exec flag. The shell does not change the container's main command.

The bundled Docker CLI and Python's POSIX PTY support provide the backend; xterm.js renders the shell. Authenticated same-origin operations carry input, resize events, and bounded output over short HTTP polls, preserving the existing Waitress server. Output stays in memory and is not written to application logs. There are at most eight terminals per process, with five-minute cleanup after the last input/resize. Disconnect and navigation close the local CLI connection; background commands started inside the container may continue. There is no session reconnection or cross-instance session sharing. Multi-replica deployments require sticky routing. Demo mode refuses terminal and image-pull execution.

On a Swarm target, Local containers terminals access containers visible to the connected engine. For worker tasks, use Open node terminal from Tasks or the service child rows. The Swarm adapter uses the relay described below; it never SSHs into workers.

Scope and verification¶

Container creation currently uses the image's default command, creates the container stopped, and requires an image already present. Pull the image first. Image pull uses target-scoped registry credential files and has a 120-second timeout. Configure registry profiles through Settings; see registry credentials and Git sources. Without profiles, the CLI uses /etc/declarack/docker. Network creation defaults to a local bridge for standalone Docker and an overlay for Swarm; it is sent to the connected engine or manager. Removal never forces deletion and container removal never deletes its volumes.

Unit tests exercise non-force requests, terminal command arguments, limits, socket isolation, binary output, input size bounds, and versioned service restart. Live smoke tests use disposable Alpine containers to verify interactive exec, resize, and disconnect. Existing workloads are not used for mutation tests.

On-demand volume sizes¶

In Volumes, choose Collect volume sizes to fetch inventory plus disk usage. Inventory loads automatically when the Volumes page opens and when the top-level Refresh button is pressed. Size measurement remains an explicit action. Docker disk usage likewise loads automatically when its page opens. Sizes use Docker's /system/df?type=volume response and display decimal MB/GB with the collection timestamp. A measured empty volume shows 0 MB; missing/unsupported usage shows Unavailable, while inventory-only results show Not collected. No size is inferred from a mount path, and unavailable values are never treated as zero. Refreshing inventory clears the previous size snapshot.

On Swarm, collection runs as a read operation through the existing short-lived node jobs, for one node or all selected nodes. Each result retains node identity; node errors remain visible alongside successful results. Publish and configure the updated image for both the dashboard and DECLARACK_AGENT_IMAGE before using this new node-agent operation. No worker SSH is used.

The generic action renderer supports immediate: true for input-free read actions and result: replace to render their response using the feature's existing YAML mapping. Failed size collection preserves the previous snapshot.

Compact inventories, paging, and full inspection¶

Inventory tables default to compact spacing. Use Compact / Comfortable to change density and Columns to reveal optional columns; preferences persist in this browser. Resource names link to dedicated detail pages. Detail summaries use a compact grid, and nested objects/arrays expand without crowding basic fields.

Tables page on the frontend with 10, 25, 50, 100, or 250 rows per page (default 25). Search filters the complete fetched inventory before paging. Changing search or page size returns to page one; pages clamp when results shrink. First/previous/ next/last controls and a visible row range show which results are displayed. The full inventory is still fetched from Docker; pagination reduces rendering, not backend payload size.

Inspect JSON explicitly fetches the complete, unprojected Docker inspect response for containers, images, networks, volumes, services, nodes, tasks, configs, and secrets. JSON is unmasked, including environment variables, labels, and driver options. Docker itself does not return secret payloads. The summary APIs retain their projections. JSON inspection is a configured, on-demand action, subject to the enabled feature allowlist. Volume inspect in Swarm uses a single-node job.

The explorer supports expandable nested trees, key/value search, expand/collapse, plain JSON text, clipboard copy, and local JSON download. Copy/download always include the entire response, even when the tree is filtered. No external JSON viewer or new backend dependency is required. Swarm volume inspection requires publishing the same updated image for the dashboard and its node jobs.

Inventory sorting¶

Click a data-column header to sort ascending; click it again for descending. Headers show a direction arrow and expose aria-sort for assistive technology. Sorting applies after full-inventory search and before pagination, and returns the table to page one. Missing values stay at the bottom in either direction. Names use natural ordering (for example, node-2 before node-10).

Columns can define a JSONata sort_value separately from their displayed value. Image/volume size columns sort by raw byte counts rather than their MB/GB labels. Run the frontend sorting checks with node --test frontend/src/lib/sort-rows.test.mjs.

Stack associations and service child rows¶

Swarm stack detail pages include collapsible sections for services, tasks/container identities, networks, configs, secrets, and declared volume references. Networks, configs and secrets include both resources labeled with the stack namespace and external resources referenced by its deployed service specs. Failures fetching one resource group are shown without hiding successful groups. Volume references do not assert that a local volume exists on a particular node; use node inventory.

Services expand into child rows in both the service inventory and stack resource sections. Children are loaded only when expanded. They use Swarm task records to show container IDs, node placement, slot, current and desired state, and errors, including historical and pending tasks. IDs link to task details; the manager API does not proxy inspect/exec for worker containers. No worker SSH is used.

Features declare children and related definitions containing an operation, JSONata input mapping, rows and columns. Related sections can declare their own children. These operations are included in the feature allowlist and checked for provider compatibility. The renderer is generic; stack association logic stays in the Swarm backend. Related tables support search, sorting, and paging.

Standalone Compose projects¶

Standalone targets can enable features: [compose, containers, images, networks, volumes, disk_usage]. The default target and example config include Compose. Discovery uses docker compose ls --all --format json, with a Docker project-label fallback if the CLI is unavailable. Stopped projects are included. Project detail pages show related containers, networks and volumes, followed by source settings and lifecycle controls, using the same YAML-driven renderer as stacks.

Save an inline Compose file or choose an explicitly mounted folder beneath stack_root (or DECLARACK_STACK_ROOT). Preview resolves Compose configuration and supplies a digest; up/update, start, stop, restart and down refuse a stale digest. Up and down optionally remove orphaned project containers. Down retains volumes and saved sources. Source files are private files under the target's data directory. GitHub-backed Compose sources and a destructive clear-volumes workflow are not implemented in this version.

Docker's ConfigFiles label reports paths on the original Docker host. These are metadata, not proof the dashboard can read those files. Existing projects can be viewed without importing their sources, but lifecycle actions require an explicitly saved accessible source. Relative bind mounts resolve from the dashboard's source path; use matching absolute paths on the Docker host (or absolute bind paths in the Compose file). External resources without project labels are not enumerated by the project resource view. The runtime image includes the Compose CLI plugin. BuildKit-only Compose build features require a separately mounted Buildx CLI plugin; it is not bundled in the small default runtime. Standard deployments using published images do not need that plugin.

Swarm worker terminal adapter¶

Configure a Swarm target's agent_image to the same published image/digest as the dashboard. Nodes must be able to pull it, including registry authentication where needed. Open a running task's terminal through Tasks or a service/stack child row.

The swarm.terminal executor verifies the task is running, resolves its actual container and node on the manager, and creates two per-session replicated jobs: a socket-mounted relay pinned to the target node, and a socket-free bridge pinned to the connected manager. They use an encrypted, internal, non-attachable overlay with no published ports. A random session token authenticates the bridge to the relay. The dashboard execs into the manager-local bridge; the bridge streams input, output and resize events to the worker relay. No worker SSH, worker Docker TCP listener, permanent agent, public callback, or WebSocket dependency is required.

The selected node and connected manager must both be ready, active Linux nodes; a drained manager cannot schedule the temporary bridge. There are at most four Swarm terminal sessions per dashboard process (within the generic eight-terminal limit), five-minute input/resize idle cleanup, and a fifteen-minute relay lifetime. Disconnect/error removes both jobs and retries overlay removal after endpoints are released. Expiry labels allow the manager job cleanup loop to remove expired services/networks after a dashboard restart. Shell processes/background commands inside the target container can outlive a dropped exec connection. Multi-replica GUI deployments require sticky sessions because sessions are in memory.

Live tests validated Compose lifecycle on disposable projects and the two-job terminal transport, authentication path, input/output, resize and cleanup on the local single-node Swarm. Separate physical worker hosts were not available for a multi-host integration test; unit tests verify distinct worker/manager placement and scope validation. Normal Swarm encrypted-overlay connectivity is required.

Viewing discovered host Compose files¶

An optional read-only host mount enables View host Compose files on discovered project pages. Set DECLARACK_COMPOSE_HOST_ROOT=/mnt/host, or host_root per target. A reported /srv/app/compose.yaml maps to /mnt/host/srv/app/compose.yaml. Discovery checks file metadata; file contents are read only by the explicit viewer action. The viewer handles multiple reported config files without importing or deploying them. Original files and the project's saved source remain unchanged.

Native Linux can use compose.host-files.yaml to bind / read-only at /mnt/host. Docker Desktop macOS should use compose.host-files.macos.yaml, which preserves /Users/... paths under /mnt/host/Users/.... Binding Desktop's / exposes the Linux VM root and does not provide the original macOS Compose paths.

The reader confines resolved paths to the configured mount, opens components without following replacement symlinks, permits regular UTF-8 files only, and bounds each file to 512 KiB and combined content to 2 MiB (up to 16 reported files). Missing files and read errors are returned per file. Remote SSH engine targets never inherit the local global filesystem mapping; configure their own matching mount explicitly. Host-root mounts are opt-in and may be narrowed to project roots.

Real two-Swarm lab¶

The multi-environment lab runs two independent Docker-in-Docker Swarms with one manager and worker each. It exercises manager SSH tunnels, actual worker-scheduled services, host standalone inventory, Prometheus/Grafana direct and SSH access, node-local volume jobs on all four nodes, and an interactive terminal into a worker task through Swarm relays.

Container and network inventories now aggregate selected/all Swarm nodes through same-image jobs. Node-qualified row identity keeps duplicate names separate. Worker rows offer node-pinned inspection and, for running task containers, the Swarm terminal relay. Direct worker lifecycle mutations remain unavailable. Manager-engine lifecycle actions are confirmed and refreshed in place; use service actions for durable Swarm workload changes. Non-confirmation row forms stay beneath their resource, while destructive confirmations remain modal. See the scope and placement contract.

Task identity and relationships¶

Task lists and details resolve service names and node hostnames through batched manager lookups. They show the task attempt, slot, image, container identity and state; full IDs remain available in details and optional columns. Removed services or nodes are labeled explicitly, and unavailable name lookups retain the task with a context warning. Declarack helper tasks are excluded from the list. Inspect container reads from the owning node through a short-lived job; an old task can reference a container Docker has already removed. This action may report unavailable rather than return container data. Task JSON inspection continues to return the original manager task response.
