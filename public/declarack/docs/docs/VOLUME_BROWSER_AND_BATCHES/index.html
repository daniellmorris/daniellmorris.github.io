Volume browsing and multi-target operation pages¶

Read-only volume file browser¶

Open a Docker target's Volumes, collect inventory, then select Browse files on a volume row. Swarm rows retain their node ID, so identical local volume names on different nodes remain distinct. Browsing opens a dedicated page, not a modal.

Directories support navigation, Up, refresh, and pages of 200 entries. Selecting a regular file previews UTF-8 text when possible and offers a binary-safe download. The first version is deliberately read-only: there is no upload, file write, rename, mkdir or delete API. Files larger than 64 KiB cannot be previewed/downloaded; directories larger than 5,000 entries return an explicit limit error. Permission errors remain errors. Symlinks, devices and FIFOs are not followed. Relative paths are resolved by directory descriptors with no-follow opens rather than trusting a string prefix. Data never needs to be exposed by mounting the host root into the GUI container.

The target must supply agent_image, or the process must supply DECLARACK_AGENT_IMAGE, naming the same Declarack image version as the backend:

targets:
  docker:
    connection: docker_socket
    socket: /var/run/docker.sock
    agent_image: ghcr.io/daniellmorris/declarack:latest
    features: [volumes]

Use a pinned release/digest in production and make it available on the relevant engines. The helper path does not perform an implicit image pull. Driver-backed volumes must be mountable by Docker; this is not a host-path fallback.

  • Standalone: inspect the existing volume, create a temporary same-image container with only that volume mounted read-only, no network, a read-only root filesystem, dropped capabilities, and no-new-privileges. Collect its result and remove the helper. This also works through a managed manager/host SSH tunnel.
  • Swarm: first inspect the volume on the selected node through a socket job, then run a node-pinned job mounting only that volume read-only. No worker SSH is used, and the file-reading job does not receive the Docker socket. The image must be present/pullable on the selected node. Jobs use the existing lifecycle cleanup.

Inspection prevents normal accidental creation of nonexistent volumes. Docker volume mounting and inspection are separate requests: a concurrent external volume deletion/recreation is not an atomic storage snapshot. Do not remove or replace a volume while browsing it. A failure after helper creation, or a process crash, can require normal Docker cleanup; browser helpers carry the label io.declarack.volume-browser=1.

The feature YAML declares a file_browser action and hidden read operation. The generic browser receives those operation names; Docker-specific execution and node selection remain in the adapter. Operations are volumes.files.list and volumes.files.read, with name, optional path/offset, and a required node_id in Swarm. They are on demand and never scheduled from an environment summary.

Configured multi-target batches¶

A batches section defines top-level pages that run one enabled operation against several targets. This is generic orchestration, not a new pseudo-SSH target. SSH remains responsible for connecting, executing commands and collecting metrics. Target/environment membership remains independent.

targets:
  server_a:
    connection: ssh
    host: server-a.example.com
    features:
    - host_metrics
    - ssh_commands
    credential: ssh_server_a
  server_b:
    connection: ssh
    host: server-b.example.com
    features:
    - host_metrics
    - ssh_commands
    credential: ssh_server_a
environments:
  servers:
    label: SSH servers
    targets:
    - server_a
    - server_b
    batches:
    - metrics
    - command
batches:
  metrics:
    title: Fleet metrics
    operation: host.metrics
    columns:
    - label: CPU percent
      value: result.cpu
    - label: Memory available MB
      value: $round(result.memory.MemAvailable / 1000000, 1)
    - label: Disk available GB
      value: $round(result.disk.available / 1000000000, 2)
  command:
    title: Fleet command
    operation: ssh.command
    confirmation: Run this command on all selected SSH hosts?
    columns:
    - label: Output
      value: $substring(result.text, 0, 500)
credentials:
  ssh_server_a:
    type: ssh
    username: operator
    private_key:
      file: /run/secrets/ssh_key
    known_hosts:
      file: /etc/declarack/known_hosts

Save and reload configuration. Open the SSH servers environment to access its batches. Select a subset of that environment’s hosts, fill the operation's declared inputs, and run. Command batches show a confirmation dialog including the hosts and input values. There is no scheduling, automatic retry or transaction rollback for batch changes. Metrics run only when requested. SSH Linux metrics require remote python3 and readable /proc; commands use the configured SSH account's permissions, not an implicit sudo/root escalation.

Each host returns its own success/error and duration. One host failure does not cancel the others. Output tables use JSONata against {target, label, ok, result, error, duration_ms}; Full result expands the structured response. These are execution results, not historical monitoring records. Use checks for persisted monitoring. A successful command exit does not prove its intended external effects.

Limits: 32 batch pages, 1–32 targets per page, four concurrent executions per run, and 64 KiB of result per target. Commands run through the existing 20-second SSH command timeout and output cap; supplied ssh.command input is additionally limited to 4096 bytes. Nonzero exit and transport failures are isolated error rows; failed-command stdout/stderr is not currently returned. No automatic retry is made because a failed connection can leave a remote command's outcome uncertain.

The same operation must be enabled on every configured target, with identical input schemas. This does not grant access to disabled target operations or arbitrary unconfigured hosts. Actions require a configured confirmation message; read-style primary operations can omit one. A custom read operation is an administrator's assertion about its behavior, not an automatic safety classification. Do not use a modifying operation as an unconfirmed read.

POST /api/v1/batches/<id>/run accepts {targets, inputs, confirmed}. targets can only narrow the configured list. Actions require confirmed: true in addition to the standard authenticated X-Declarack-Action: 1 protection.

Real lab example¶

The engine image now includes Python for SSH metric collection. Existing engines need that package installed, or a rebuild through the lab's normal up workflow. Copy examples/multi-environment/optional/tools.yaml into the runtime config folder and reload. It adds two explicit SSH manager-host targets, a group, and command and metric batch pages. Swarm worker access still uses jobs exclusively. Because this lab uses DinD containers on one Docker host, host /proc measurements are not independent physical machines.

The current development lab also has a dedicated sample volume named declarack-browser-demo-20261120 on standalone Docker and Swarm A's worker. Its documents/hello.txt is a safe fixture for testing navigation and previews.
