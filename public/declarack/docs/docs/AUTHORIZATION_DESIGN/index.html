Authorization design and roadmap¶

The initial configuration-backed role model is implemented. See the authorization guide for current schema, API behavior, verification and limits. This document preserves the broader design: per-resource constraints, granular installation APIs, partial dashboard redaction and scoped background delegation remain roadmap items rather than shipped guarantees.

Recommended model¶

Use roles that grant named permissions within explicit scopes. Adapter operation IDs are the natural permissions for target work; installation APIs need reserved permission IDs too. A single backend authorizer should answer:

allowed(principal, permission_id, target_id=None, resource=None)

Authentication establishes the principal; authorization decides each request. Roles alone are insufficient without target scope: permission to stop a container on a test host must not grant that operation on a production host. Environments organize navigation and can overlap; they are not security boundaries by default. Start with explicit target IDs. Environment-derived target selectors can follow later, with clear warnings that changing membership changes access.

A role would grant swarm.services.list, swarm.services.inspect, swarm.services.scale and swarm.services.restart on target production-a, while granting no user administration, raw container inspection or shell access. Represent this as a list of grants, each with permission IDs and target IDs, rather than independent global lists that accidentally create a cross-product.

Use default deny and the union of explicit role grants in the first version. Avoid deny-rule precedence, resource-label policies and arbitrary policy scripting until there is a concrete need. New custom operations should not become authorized automatically because their names match a broad viewer wildcard. Built-in administrator access is an explicit privileged role.

Permissions beyond target operations¶

Reserve installation-level IDs, for example system.users.read, system.users.manage, system.roles.manage, system.config.read, system.config.review, system.config.save, system.config.activate, and credential permissions for use, management and disclosure. These are proposed names, not shipped operation IDs. Self-service account actions should be distinct from managing other accounts.

  • Configuration and adapter-definition editing are effectively administrative: they can add commands, change target connections or alter an already granted operation's meaning. Keeping the same operation ID must not bypass a review of changed effects. Limit this editing to trusted installation administrators.
  • Credential use is different from credential disclosure. An operator can be allowed to use a target's registry authentication without retrieving its PAT. Grants must not allow arbitrary selection of another target's credential.
  • Raw inspection and configuration reads can disclose environment variables, credential values and mounts. Read-only does not automatically mean low risk.
  • An arbitrary SSH command or interactive shell is code execution within its target's privileges. Grant these explicitly; do not include them in an observer role simply because their transport uses a read endpoint.

Derive the UI from effective permissions¶

The backend should return effective capabilities alongside filtered metadata. Use the same decision function for rendering hints and actual execution:

UI element Required access
Target/navigation group At least one accessible feature on that target
Resource list Its inventory operation
Resource detail Its inspect operation and any explicit detail dependencies
Action Its operation and applicable target/resource scope
Create/edit workflow Required lookups, preview and execute operations
Custom dashboard Each authorized source, independently
Settings section Its installation permission
Terminal Open permission plus matching session ownership and transport access

A feature is a presentation bundle, not the security unit. A user might view services but lack scale or delete, or view a summary but lack sensitive inspect. Role editing should explain required dependencies and offer maintained capability bundles instead of requiring administrators to discover every transport operation. Dependency resolution must not silently grant unrelated write operations.

Mixed-target dashboards should omit unauthorized sources without describing them as failed targets. Do not leak hidden target names, resource counts or data via aggregates, exports, searches, filters, errors or historical results. Define how partial dashboards render before exposing them to restricted users.

Operation outputs also form part of the permission contract. For example, swarm.tasks.list resolves service names and node hostnames internally. Granting that operation grants its documented result, not general permission to execute all service/node APIs. Similarly, a node-local read may internally create a short-lived Swarm job; authorization should cover the requested operation and its scope, not expose helper-job creation as a separate user power.

Enforce at every entry point¶

Filtering buttons is usability, not enforcement. Named operation dispatch, direct Docker routes, settings/users/credentials APIs, bulk previews and execution, terminal/file transports, downloads, run history and scheduled execution all need the same authorization boundary. A direct URL or crafted request must not bypass it. Internal dependencies execute on behalf of the authorized operation, not as an unrestricted user-callable shortcut.

Bind terminal/file sessions to the principal, target and resource. Possessing a session token alone should not authorize another user to read or write it. Audit and run history also need ownership/visibility rules because results can be sensitive. Keep permitted execution scope even when work moves to a worker job.

Recheck permission at execution, not only during preview. Role revocation must invalidate stale capability metadata, reviewed writes and new background steps. Existing approvals/digest/version checks remain necessary and complementary. In-flight external effects cannot always be undone; document revocation behavior rather than promising rollback of a Docker operation already issued.

Scheduled checks and jobs need explicit, scoped service principals or delegated identities. They must not silently acquire all installation-admin privileges, or retain a user's old access forever after role changes. Define delegation and revocation before enabling non-admin schedule creation.

Storage and rollout¶

Role definitions and permission grants belong in system configuration. User accounts and assigned role IDs belong in the account database. The backend derives effective access from those assignments and the active configuration.

The database already owns saved and active system configuration. Role definitions therefore reuse the existing file import, GUI editing, review, save, history and activation workflow rather than introducing a second policy store. Files remain import/write-back sources under the existing FORCE_LOAD/WRITE_BACK rules.

Saving role changes does not change access until activation. Requests, reviewed writes, terminal sessions and background execution must observe the active policy revision. Role assignments take effect when their account change commits; both kinds of change invalidate stale effective-access metadata. Record changes in the audit log without recording credential values.

Keep a protected built-in Administrator role outside editable role definitions, so configuration cannot accidentally remove installation recovery. Migrate existing administrators explicitly to that role. Validate references when saving assignments and when activating configuration. Referenced role removal should require reassignment; a force-loaded configuration with unresolved assignments must fail closed for those grants while preserving built-in administrator access. Activation and account edits must protect the last enabled administrator, with consistent transactional/concurrency checks. Editing configuration or assignments must not let an operator elevate their own access beyond delegated authority.

Recommended implementation order:

  1. Inventory every externally reachable operation/API, classify its effect and sensitivity, and define the shared authorizer and operation dependency model.
  2. Implement roles with per-target grants plus installation permissions; enforce them on all entry points, including session/run ownership. Keep background administration privileged until scoped delegation exists. Test direct requests as well as filtered UI metadata.
  3. Add role assignment and an effective-access preview to Users, with initial Administrator, Observer and Operator presets. Presets list explicit permissions.
  4. Add scoped background identities, resource/argument constraints and optional environment selectors where real workflows require them.

Resource constraints such as “scale only this service, up to five replicas” are useful later. They require adapter-aware resource resolution and fresh validation; operation names alone cannot express them. Keep the policy evaluator generic and let adapters supply the resource context it evaluates.
