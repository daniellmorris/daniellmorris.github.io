Deployment and persistence¶

The application image contains Python, the built frontend and required Docker/SSH clients. The documentation site is a separate static build; none of its packages are installed in the runtime image.

Production essentials¶

Use a strong first-administrator bootstrap password, persist the database and required local files, and mount only the sockets/files your targets need. The repository Compose file binds HTTP port 8080 to loopback. For remote access use native TLS or an HTTPS reverse proxy with explicit immediate-proxy trust. HTTP remains available for local development.

Local administrators sign in with cookie sessions; all have full installation, credential and workload access. Environment groups do not supply per-user permissions. SSO, teams and granular RBAC are not implemented. Bootstrap inputs seed an empty user database only; later password changes belong in Settings → Administrators or host recovery.

See administrators, sessions and TLS for first-account files, recovery, cookie/CSRF clients and the breaking Basic Auth migration. Native TLS uses DECLARACK_TLS=files with mounted certificate/key paths, or DECLARACK_TLS=self-signed with persisted /data/tls identity. The default TLS port is 8443, so adjust container port mappings. Certificates load on restart; there is no ACME or automatic renewal. Behind a TLS proxy, configure DECLARACK_TRUSTED_PROXIES with explicit IPs/CIDRs to recognize HTTPS and set Secure cookies. Only one forwarded proto/client hop is trusted; host/prefix are not.

Match the controller and node image¶

In Swarm, publish the same image for the controller and node-local jobs. Set DECLARACK_AGENT_IMAGE to that reference, preferably an immutable registry digest. Every participating node must be able to pull it. The build workflow reports the published digest; a controller-local image alone is not a registry deployment.

Node jobs require compatible Linux engines and eligible ready/active nodes. Metrics remain on demand by default. Worker SSH is not part of Swarm collection.

What to persist¶

State Location / requirement
System configuration Active/saved database revisions; mounted files or other providers are import/publication sources
Administrators, hashed sessions, login limits, Stack/Compose sources, checks, operations and configuration revisions Shared database: SQLite /data/state.sqlite by default, or configured PostgreSQL
Git/registry and first-account bootstrap credential references Mounted files or Docker secrets; existing users do not depend on bootstrap password files
Native TLS identity Persist /data/tls for self-signed mode; remount certificate/key files for files mode, including with PostgreSQL
Table preferences Browser storage; separate from server backups

Database setup, legacy import and backend transfer explains what is stored, how to upgrade previous installations, and what remains external. Back up the database, system configuration and operator-managed mounts together. Stop SQLite writers or use a consistent SQLite backup method; use PostgreSQL backup tools for PostgreSQL. The legacy encryption keys are included in the new database, alongside the encrypted source credentials.

Configuration storage choices¶

Folder storage supports atomic GUI source-file saves and new integration fragments. File storage supports its existing restricted settings edits. Git storage opens configuration pull requests; merging does not itself update a running mount. Swarm config storage updates the controller service's config attachment and redeploys it. Their bootstrap requirements and edit restrictions are in the system reference.

One controller for local persisted services¶

Checks and operation plans are process-owned, with SQLite or PostgreSQL storage. Do not treat multiple controllers sharing a data volume as a distributed scheduler or queue. A backend restart marks abandoned plans interrupted when inspected; it does not resume them automatically. Inspect resources and run metadata before retrying.

Existing health sources and persisted checks are distinct from outbound alerting: Declarack currently records local alarm/recovery state but does not send notifications.
