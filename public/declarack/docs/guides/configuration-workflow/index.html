Work with a configuration folder¶

For the model, hierarchy diagrams and a complete example, start with How configuration fits together. For environment forms, use Settings → Home & environments and follow the structured editing workflow.

Use a folder when you want editable source files and guided integration setup. It is one system configuration assembled from ordered fragments, not a collection of independent plugin installations.

Current save and activation behavior¶

The database owns configuration. The file/folder below seeds an empty installation; GUI edits save logical documents in the database, then Activate configuration applies them. Use Review import from files after external edits, or set DECLARACK_CONFIG_FORCE_LOAD=1 to import at each startup. Enable DECLARACK_CONFIG_WRITE_BACK=1 for GUI activation to update local files. Both flags default off. A writable source mount is only required for write-back, not DB-only editing. See storage and recovery. The older screenshots show the former source-file Save/Reload labels; the same review workflow now saves and activates database revisions.

Start from the supplied example¶

From the repository root:

cp -R configurations/folder-example my-config

Create a deployment override named compose.local-config.yaml:

services:
  declarack:
    environment:
      DECLARACK_CONFIG: /etc/declarack/config
      DECLARACK_CONFIG_EDIT: '1'
    volumes:
      - ./my-config:/etc/declarack/config

Start it alongside the base Compose file, which supplies the password, socket and persistent data volume:

export DECLARACK_PASSWORD='choose-a-strong-local-password'
docker compose -f compose.yaml -f compose.local-config.yaml up -d --build

Open the GUI on port 8080. Settings should list source files and show New file, file editing and Reload configuration. If the directory is mounted read-only, external edits/reload still work but GUI saves do not.

Add an integration¶

  1. Open Targets → Add integration.
  2. Choose the transport/system template. Enter a unique target ID and display name.
  3. Supply paths as seen inside the Declarack container. Mount SSH keys, known_hosts and credential files before referencing them.
  4. Select an existing environment ID, enter a new ID, or leave it blank.
  5. Review the generated YAML and optionally test the connection.
  6. Save, then reload. Edit saved YAML opens the new fragment directly in Settings.

The wizard adds a new file and preserves existing source files. A failed connection test does not prevent storing an intentionally offline target. Review and save still require a valid merged configuration. Single-file, Git and Swarm-config storage retain their existing editing workflows; wizard saves currently require a folder.

Walk through a Custom HTTP API integration¶

These captures use the local training API on your host and the folder-backed tutorial instance. Choose Custom HTTP API and use training-copy, Training copy, origin http://127.0.0.1:9010, endpoint /apps, rows items, and environment tutorial. This adds a separate connection to the same synthetic API. In a container deployment, use an address reachable from that container instead of this host-process loopback address.

Understand the merge¶

Paths sort case-sensitively. Mappings merge recursively. Lists and scalar values are replaced by later values. For example, a later features: [containers] replaces an earlier feature list; it does not append to it.

A simple convention is system settings first, targets next, pages/checks afterward, and deliberate overrides last. Generated integration files use sequential names under zz-integrations/ to preserve successive environment membership updates.

Edit and reload deliberately¶

  • Edit a selected file, then choose Save file. The prior source is retained as .previous; saving does not apply it.
  • Choose Reload configuration to validate the entire source and apply it.
  • If another writer changed a file, read source files again before retrying a save.
  • Authentication and legacy-workspace changes require restart. Adapter code changes also require restart; ordinary YAML definitions can be reloaded from the folder.

The merged preview is read-only because its values may come from several files. A .previous file is a preceding-source backup, not a full revision history/rollback UI.

Create another file¶

Choose New file, provide a relative .yaml path and enter a configuration mapping. Review new file validates the entire proposed merge and displays source and effective-config diffs. Save file writes it without overwriting an existing path; reload afterward to apply it. The empty mapping shown below is a harmless starting point; replace it with your actual definitions before creating a useful feature, page or check.

Test all targets¶

Choose Test all connections to see a separate Passed/Failed result for every target in the displayed configuration. Testing does not save or apply changes.

Review and restore revisions¶

Select a source file and choose Review & save file after editing. Inspect the source diff, expand Effective merged configuration diff, or inspect Preview merged configuration. Choose Back to editing to adjust the draft, or Save file and then Reload configuration to apply it.

Open Revision history, choose an earlier snapshot, and select Restore to draft. This loads the selected file without writing or applying it. Review and save it through the same flow. Local history retains 20 snapshots per source and needs a persistent data directory. See the recovery rules for retention and provider limits.

The screenshots above show the earlier editor; the current editor inserts the review step between editing and saving.

Start from an example¶

Open Example snippets in Settings to search by task or filter by category. Examples cover targets, custom API tables, confirmed actions, environment groups, multi-target dashboards, checks, and SSH fleet operations. The right pane explains what to adapt and links to prerequisite examples. Copy YAML copies the selected fragment; it does not change the editor or the running configuration. Paste into New file or merge it into an existing draft, then review, save and reload. Prerequisites belong in separate source files unless their mappings are explicitly merged. The snippet library publishes the same YAML in the docs.
