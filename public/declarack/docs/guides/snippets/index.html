Configuration snippet library¶

In Declarack, open Settings → Example snippets to search these examples and copy YAML. These are fragments: add prerequisites as separate YAML files first, adapt placeholders and IDs, then review, save and reload. Files merge in filename order. Lists replace earlier lists. Copying an example does not save or apply configuration.

SSH examples need mounted identity and known-hosts files. Checks start scheduling after reload; persist the data directory for history.

Standalone Docker¶

Targets — Connect to a local Docker socket, including Compose projects.

Mount the Docker socket into Declarack. This grants control of the engine. Replace example_docker if you already have a local target.

Suggested filename: 10-local-docker.yaml.

targets:
  example_docker:
    label: Example local Docker
    connection: docker_socket
    socket: /var/run/docker.sock
    swarm: false
    features: [compose, containers, images, networks, volumes, disk_usage]

Swarm manager over SSH¶

Targets — Reach a remote Swarm through an SSH tunnel to its manager.

Replace the manager hostname and user; mount existing SSH key and known-hosts files. The SSH user needs Docker access. Swarm node-local work uses jobs, not SSH to workers.

Suggested filename: 10-remote-swarm.yaml.

targets:
  example_swarm:
    label: Example Swarm
    connection: docker_socket
    swarm: true
    ssh_tunnel:
      host: manager.example.com
      remote_socket: /var/run/docker.sock
      credential: tunnel_example_swarm
    agent_image: ghcr.io/daniellmorris/declarack:latest
    features:
    - overview
    - services
    - nodes
    - tasks
    - stacks
    - configs
    - secrets
    - networks
    - volumes
credentials:
  tunnel_example_swarm:
    type: ssh
    username: declarack
    private_key:
      file: /run/secrets/manager_ssh_key
    known_hosts:
      file: /etc/declarack/known_hosts

Linux host over SSH¶

Targets — Collect on-demand Linux host metrics and expose command execution.

Replace the hostname and user; mount existing SSH key and known-hosts files. Metrics require python3 on the remote host; commands run as the configured user.

Suggested filename: 10-ssh-host.yaml.

targets:
  example_ssh:
    label: Example Linux host
    connection: ssh
    host: host.example.com
    features:
    - host_metrics
    - ssh_commands
    credential: ssh_example_ssh
credentials:
  ssh_example_ssh:
    type: ssh
    username: declarack
    private_key:
      file: /run/secrets/host_ssh_key
    known_hosts:
      file: /etc/declarack/known_hosts

Custom HTTP API¶

Targets — Define an HTTP target that a custom feature or check can use.

Replace base_url with your API. This target intentionally has no navigation features until the table snippet is added. The examples assume JSON responses.

Suggested filename: 10-http-api.yaml.

targets:
  example_api:
    label: Example application API
    connection: http
    base_url: https://api.example.com
    features: []

API table with filters and details¶

Features — Map a JSON items array into a searchable resource table with detail pages.

Assumes GET /items returns {"items":[{"id":"1","name":"Example","status":"running"}]} and GET /items/1 returns one item. Adapt paths and JSONata mappings. The features list replaces the earlier list.

Requires: Custom HTTP API (including their prerequisites), or equivalent existing definitions.

Suggested filename: 20-api-table.yaml.

operations:
  example.items.list:
    bindings:
      http:
        executor: http.request
        path: /items
  example.items.inspect:
    bindings:
      http:
        executor: http.request
        path: /items/{id}
        inputs:
          id: {type: string}
features:
  example.items:
    title: Example items
    group: Applications
    operation: example.items.list
    rows: items
    columns:
      - {label: Name, value: name}
      - label: Status
        value: status
        badges: {running: active, stopped: muted}
    filters:
      - key: status
        label: Status
        value: status
        choices: {running: Running, stopped: Stopped}
    details:
      operation: example.items.inspect
      row_id: id
      input: id
      title: name
      fields:
        - {label: Name, value: name}
        - {label: Status, value: status}
targets:
  example_api:
    features: [example.items]

Confirmed row and bulk action¶

Actions — Add a restart action with an icon and confirmation to the example table.

Assumes POST /items/{id}/restart. This performs a real mutation when clicked; adapt it to your API. The actions list replaces any earlier actions list.

Requires: API table with filters and details (including their prerequisites), or equivalent existing definitions.

Suggested filename: 30-api-action.yaml.

operations:
  example.items.restart:
    bindings:
      http:
        executor: http.request
        method: POST
        path: /items/{id}/restart
        inputs:
          id: {type: string}
features:
  example.items:
    actions:
      - label: Restart item
        icon: restart
        operation: example.items.restart
        row: {id: id}
        bulk: true
        confirmation: Restart the selected items?

Group targets into an environment¶

Environments — Show Docker and an application API together in one environment.

Targets carry their features. An environment groups targets and can also reference custom pages. Replace IDs to group your existing targets.

Requires: Standalone Docker, Custom HTTP API (including their prerequisites), or equivalent existing definitions.

Suggested filename: 30-environment.yaml.

environments:
  example_workspace:
    label: Example workspace
    targets: [example_docker, example_api]

Dashboard across Docker and Swarm¶

Dashboards — Combine sources from two engines into cards, tables and a chart.

Sources are queried on page load. JSONata expressions refer to source results by name. Replace target IDs to use existing engines.

Requires: Standalone Docker, Swarm manager over SSH (including their prerequisites), or equivalent existing definitions.

Suggested filename: 40-cross-target-dashboard.yaml.

pages:
  example_operations:
    title: Example operations dashboard
    sources:
      local:
        target: example_docker
        operation: containers.list
      swarm:
        target: example_swarm
        operation: swarm.services.list
    cards:
      - label: Running local containers
        value: $count(data.local[State = "running"])
      - label: Swarm services
        value: $count(data.swarm)
    panels:
      - title: Swarm replicas
        sources: [swarm]
        rows: data.swarm
        target: example_swarm
        feature: services
        row_id: ID
        columns:
          - {label: Service, value: Spec.Name}
          - label: Running / desired
            value: '$string(ServiceStatus.RunningTasks) & "/" & $string(ServiceStatus.DesiredTasks)'
            sort_value: ServiceStatus.RunningTasks
            tone: 'ServiceStatus.RunningTasks < ServiceStatus.DesiredTasks ? "destructive" : "active"'
    charts:
      - title: Workloads by target
        type: bar
        rows: '[{"target":"Docker","count":$count(data.local)},{"target":"Swarm","count":$count(data.swarm)}]'
        x: target
        series:
          - {label: Workloads, value: count}

Environment-only custom page¶

Dashboards — Limit the example dashboard to a specific environment.

Root pages are explicitly empty. The team environment includes the page. This controls page placement, not user authorization.

Requires: Dashboard across Docker and Swarm (including their prerequisites), or equivalent existing definitions.

Suggested filename: 50-page-scope.yaml.

environments:
  root:
    pages: []
  example_operations_team:
    label: Example operations team
    targets: [example_docker, example_swarm]
    pages: [example_operations]

Scheduled connection check¶

Checks — Check a target connection with failure and recovery thresholds.

No operation means connector-level connection testing. Scheduled checks begin after the configuration is applied. Persist /data for check history.

Requires: Custom HTTP API (including their prerequisites), or equivalent existing definitions.

Suggested filename: 30-connection-check.yaml.

checks:
  example_api_connection:
    title: Example API connection
    target: example_api
    every: 60s
    failure_threshold: 3
    recovery_threshold: 2

Scheduled JSON health check¶

Checks — Evaluate a JSON readiness response with JSONata.

Assumes GET /health returns {"status":"ok"}. Adapt the path and healthy expression. Use eligible reads for scheduled operations; persist /data for history.

Requires: Custom HTTP API (including their prerequisites), or equivalent existing definitions.

Suggested filename: 30-http-health-check.yaml.

operations:
  example.health:
    check_safe: true
    bindings:
      http:
        executor: http.request
        path: /health
checks:
  example_api_health:
    title: Example API readiness
    target: example_api
    operation: example.health
    healthy: status = "ok"
    every: 30s
    failure_threshold: 2
    recovery_threshold: 1

Metrics across SSH targets¶

SSH fleets — Aggregate Linux host metrics across a selected set of SSH targets.

Add more SSH target IDs to the targets list. Metrics are requested on demand, not continuously collected.

Requires: Linux host over SSH (including their prerequisites), or equivalent existing definitions.

Suggested filename: 30-ssh-fleet-metrics.yaml.

batches:
  example_fleet_metrics:
    title: Example fleet metrics
    operation: host.metrics
    columns:
      - {label: CPU percent, value: result.cpu}
      - label: Available memory MB
        value: $round(result.memory.MemAvailable / 1000000, 1)
      - label: Available disk GB
        value: $round(result.disk.available / 1000000000, 2)

environments:
  example_fleet_metrics:
    label: Example SSH metrics
    targets: [example_ssh]
    batches: [example_fleet_metrics]

Command across SSH targets¶

SSH fleets — Run an operator-supplied command on selected SSH hosts with confirmation.

Add more SSH target IDs to the targets list. Commands run with the configured SSH user privileges; this is interactive fleet execution, not a scheduled check.

Requires: Linux host over SSH (including their prerequisites), or equivalent existing definitions.

Suggested filename: 30-ssh-fleet-command.yaml.

batches:
  example_fleet_command:
    title: Example fleet command
    operation: ssh.command
    confirmation: Run this command on every selected SSH host as its configured user?
    columns:
      - label: Output
        value: $substring(result.text, 0, 1000)

environments:
  example_fleet_command:
    label: Example SSH command
    targets: [example_ssh]
    batches: [example_fleet_command]

Registry credentials for Docker¶

Credentials — Registry credentials for Docker. File-backed references keep credential values outside the configuration.

Mount the registry token file first. Credentials apply to this target’s image pulls and Compose operations by image hostname. Use docker.io for Docker Hub; Git tokens are separate.

Requires: Standalone Docker (including their prerequisites), or equivalent existing definitions.

Suggested filename: 20-registry-credentials.yaml.

targets:
  example_docker:
    registry_credentials:
      ghcr.io: registry_ghcr.io
credentials:
  registry_ghcr.io:
    type: basic
    username: example-user
    password:
      file: /run/secrets/ghcr_token

Git and registry credentials for Swarm¶

Credentials — Git and registry credentials for Swarm. File-backed references keep credential values outside the configuration.

Mount referenced files and replace hosts/users. In the stack editor choose Git repository, enter HTTPS or ssh:// URL and a branch/tag/commit, then select the credential. Registry auth is forwarded to workers during deployment.

Requires: Swarm manager over SSH (including their prerequisites), or equivalent existing definitions.

Suggested filename: 20-swarm-source-credentials.yaml.

targets:
  example_swarm:
    registry_credentials:
      ghcr.io: registry_ghcr.io
    git_credentials:
    - example_https
    - example_ssh
credentials:
  registry_ghcr.io:
    type: basic
    username: example-user
    password:
      file: /run/secrets/ghcr_token
  example_https:
    type: basic
    username: deploy
    host: git.example.com
    password:
      file: /run/secrets/git_token
  example_ssh:
    type: ssh
    username: git
    host: git.example.com
    private_key:
      file: /run/secrets/git_key
    known_hosts:
      file: /etc/declarack/git_known_hosts

Named credential profiles¶

Connections — Centralize entered values or mounted-file references, then select profile IDs on connections.

Use Settings → Credentials to paste/upload values or edit paths. Replace the example secret paths. Profiles are stored in configuration and history; inline values also appear in exports and write-back files.

Requires: Standalone Docker (including their prerequisites), or equivalent existing definitions.

Suggested filename: 05-credentials.yaml.

credentials:
  example_api_token:
    type: token
    label: Example API token
    token: {file: /run/secrets/api_token}
  example_registry:
    type: basic
    label: Example registry login
    username: deploy
    password: {file: /run/secrets/registry_password}
